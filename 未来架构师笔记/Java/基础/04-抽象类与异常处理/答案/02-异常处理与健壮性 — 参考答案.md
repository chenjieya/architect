## 2. L2 原理应用

### 2.1

**答**：

- **现象**：`main` 调用 `save` 编译失败。
- **原因**：`IOException` 是受检异常，`save` 声明了 `throws`，调用方必须 catch 或继续 throws。
- **修复**：`try { save("a.txt"); } catch (IOException e) { ... }` 或 `public static void main(...) throws IOException`。

### 2.2

**答**：

- 输出顺序：**B**，然后 **C**（无 A）。
- `10/0` 抛 `ArithmeticException`，它是 `RuntimeException` 子类，被第二个 catch 捕获。
- `finally` 无论是否异常都会执行，故打印 C。
- `parseInt` 已成功，不会进 `NumberFormatException`。

### 2.3

**答**：

- **编译期**：能通过。`InsufficientFundsException` 是非受检，不要求调用方 catch。
- **运行期**：若未 catch，异常沿栈向上，线程默认处理（打印栈并终止该线程/`main`），程序可能异常结束。

### 2.4

**答**：

- **风险**：配置错误被隐藏、难以排查；线上行为与预期不符且无日志。
- **方向**：至少记录日志（含 message/stack），或 catch 后包装再 `throw`，或返回明确错误结果给上层，不要空 catch。

### 2.5

**答**：

- 改为 `RuntimeException` 后，**编译期不强制** try-catch，原有 try-catch 仍合法但非必须。
- 调用方不写 catch 时，运行期异常向上传播，可能导致程序终止，与受检「编译期督促处理」不同。

### 2.6

**答**：

- 优先看 **`NpeDemo.java:8`**（`printLength` 内）。
- 可能是参数 **`name` 为 null** 时调用了 `name.length()`。
- 向上看 **`main:15`** 谁传入了 `null`（如 `printLength(null)`）。

### 2.7

**答**：

- 能编译。
- 运行抛 **`NullPointerException`**。
- **自动拆箱**：`int value = box` 等价于 `box.intValue()`，`box` 为 null 时拆箱 NPE。

### 2.8

**答**：

- 文件不存在通常抛 **`FileNotFoundException`**（属于 **`IOException` 子类**）。
- **受检异常**。
- 因为 `readFirstLine` 声明 `throws IOException`，调用方必须处理或继续声明，否则编译不通过。

### 2.9

**答**：

- 抛 **`IllegalArgumentException`**（户主姓名不能为空），不是 NPE。
- 若先 `isEmpty` 再 `requireNonNull`：当 `owner` 为 null 时，`owner.trim()` 会先 NPE，无法在统一位置用清晰消息拒绝 null。

### 2.10

**答**：

- **B 更符合**：用 `OrderNotFoundException` 明确业务「未找到」，调用方可预期地 catch 或声明 throws。
- **A 问题**：`null` 语义不清，易在调用方引发 NPE，与业务「不存在」混为一谈。

## 3. L3 场景实战

### 3.1 [面试]

**答要点**：

- **受检**：非 `RuntimeException` 的 `Exception` 子类，编译期必须 catch 或 throws；例：`IOException`、`OrderNotFoundException`（extends Exception）。
- **非受检**：`RuntimeException` 及子类、`Error`；例：`NullPointerException`、`IllegalArgumentException`、`InsufficientFundsException`（extends RuntimeException）。

### 3.2 [面试]

**答要点**：

- **`throw`**：方法**体内**语句，创建并抛出异常实例。
- **`throws`**：方法**签名**上，声明可能抛出的**受检**异常，交给调用方处理。

### 3.3 [面试]

**答要点**：

- **finally**：收尾逻辑，几乎总执行（释放资源、记录结束等）。
- **try-with-resources**：对 `AutoCloseable` 自动 `close()`，避免忘记在 finally 关流，减少泄漏；常用于 IO。

### 3.4 [面试]

**答要点**：

- 类型名表达**业务语义**，便于分类处理与监控。
- 与参数错误、系统错误区分；消息可统一规范。
- 避免泛化 `RuntimeException` 导致调用方无法区分失败原因。

### 3.5 [面试·扩展]

**答要点**：

- **好处**：编译期督促处理可预见失败（如 IO），减少遗漏。
- **代价**：签名 `throws` 链冗长、API 演进成本高；与动态语言习惯不同。

### 3.6 [面试]

**答要点**：

- **成因**：null 引用调方法/字段、自动拆箱 null、链式调用中间为 null 等。
- **排查**：① 看异常类 ② 看 message ③ 找栈中第一个自己代码的 `at` 行 ④ Debug 查变量 ⑤ 沿栈看调用方传参。

### 3.7 [工作]

**答要点**：

- 用 **`OrderNotFoundException`**（或明确受检/非受检业务异常），禁止用 NPE 表达「不存在」。
- 约定返回值：若不用异常，用 `Optional`（后续章）或明确文档的哨兵值，且调用方必须判空/判结果，不要隐式 null。

### 3.8 [面试]

**答要点**：

- 子类异常更具体，应先匹配；父类 `Exception` 在前会捕获所有子类，后面 catch 不可达，编译失败。
- 也会丢失对不同异常分别处理的能力。

### 3.9 [面试]

**答要点**：

- **`Error`**：严重系统/JVM 问题（如 `OutOfMemoryError`），一般不由业务 catch 恢复。
- **`Exception`**：应用可处理异常。
- **`OutOfMemoryError`**：应查内存/设计，而非 `catch` 后继续当作正常流程。

### 3.10 [工作]

**答要点**：

- **问题**：每处空 catch 重复吞掉 IO 失败，问题难发现，行为不一致。
- **方向**：底层记录日志并 `throw` 包装异常（保留 cause），或由上层统一异常处理策略；`main`/入口给用户友好提示，工具方法不要空 catch。
