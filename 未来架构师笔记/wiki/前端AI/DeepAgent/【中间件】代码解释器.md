模型擅长理解和生成文字，但不擅长精确计算、筛选大 JSON 这类活。代码解释器的思路是：**让模型写一小段代码，在一个隔离环境里跑，把结果拿回来接着聊**。

先纠正一个常见误解：`CodeInterpreterMiddleware` 提供的是隔离的 JavaScript **QuickJS REPL**，**不是 Python 解释器**。QuickJS 是一个轻量级 JS 引擎，启动快、容易限制内存和执行时间，适合安全地跑模型生成的代码。

## 1. 什么时候用

比如这样的需求：

```text
请帮我审计全部退款事件：找出退款金额超过 8000 元，且 risk_tags 包含 duplicate_charge 的订单。

请按退款金额从高到低列出订单号和退款金额；不要展示其他订单，也不要展示 customer_chat_log。
```

如果靠模型自己"看"数据，既慢又容易漏。让它写几行 JavaScript 做过滤和排序，结果直接算出来，还顺带避免了把不该展示的字段喂给模型。

## 2. 配置项

```python
CodeInterpreterMiddleware(
    memory_limit=64 * 1024 * 1024,
    timeout=5.0,
    max_ptc_calls=256,
    tool_name="eval",
    max_result_chars=4000,
    capture_console=True,
    subagents=True,
    ptc=None,
    mode="thread",
    max_snapshot_bytes=None,
)
```

| 配置                 | 默认值             | 含义                                                                                                    |
| -------------------- | ------------------ | ------------------------------------------------------------------------------------------------------- |
| `memory_limit`       | `64 * 1024 * 1024` | QuickJS 堆内存上限，单位字节，即默认 64 MiB                                                             |
| `timeout`            | `5.0`              | 每次调用 `eval` 的最长执行时间，单位秒                                                                  |
| `max_ptc_calls`      | `256`              | 单次 `eval` 中，JS 通过 `tools.xxx()` 最多调用工具的次数；`None` 表示不限制，不可信输入下有无限调用风险 |
| `tool_name`          | `"eval"`           | 暴露给模型的 JS 执行工具名                                                                              |
| `max_result_chars`   | `4000`             | 执行结果和标准输出各自最多返回的字符数，超出截断；`console` 缓冲区也受此限制                            |
| `capture_console`    | `True`             | 是否提供并捕获 `console.log/warn/error`，捕获内容以 `<stdout>` 返回                                     |
| `subagents`          | `True`             | 当前 Agent 有 Deep Agents 的 `task` 工具时，是否在 JS 中提供 `task(...)`                                |
| `ptc`                | `None`             | Programmatic Tool Calling 白名单，可传工具名或 `BaseTool` 列表                                          |
| `mode`               | `"thread"`         | JS 状态保存范围，见下表                                                                                 |
| `max_snapshot_bytes` | `None`             | 状态快照的最大字节数，默认等于 `memory_limit`；超过则快照丢弃，后续无法恢复                             |

前三个是"笼子的栏杆"：内存上限、时间上限、工具调用次数上限。模型生成的代码不可信，这三个参数防止它把环境跑死或无限调工具。`max_result_chars` 则是输出栏杆——跑完返回一百万字符同样会撑爆上下文，不如直接截断。

## 3. PTC：在代码里调工具

`ptc` 是 Programmatic Tool Calling（程序化工具调用）的缩写。开启后，可以在 JavaScript 里通过 `tools.<camelCase>(input)` 调用被列进白名单的工具。

它解决的是一个很具体的浪费：如果不开启，模型要先把工具结果原样收进上下文，再写一段代码处理它；数据大时来回搬运很费 token。开启后，工具调用和数据处理都在 JS 里完成，只把最终结果回给模型。

## 4. 状态保存的三个档位

`mode` 决定 JS 环境里的变量能活多久：

| 取值       | 含义                       | 适合                       |
| ---------- | -------------------------- | -------------------------- |
| `"thread"` | 跨调用、跨轮次保存         | 需要连续处理同一批数据     |
| `"turn"`   | 只在同一轮内保存           | 一轮内多步协作             |
| `"call"`   | 每次 `eval` 都重新创建环境 | 最隔离，适合互不相关的计算 |

范围越大越方便，但也越可能把上一次的状态带进这一次的计算里，按任务需要选。

## 5. 安全边界：审批不会自动触发

这一点必须记住：**`ptc` 调用和 JavaScript 内的 `task(...)` 都不走普通 `ToolNode` 路径，因此不会为每一次内部调用触发父级的 `interrupt_on` / 人工审批**。

也就是说，你在 [[【中间件】HITL 人工审批]] 里精心配的审批关卡，对解释器内部发起的工具调用是无效的。所以给解释器开白名单时要格外克制：只放只读、无副作用的工具，写操作和高风险工具不要放进去。这是 [[【概念】驾驭工程]] 里"最小权限护栏"的一个具体落点。
