`FilesystemMiddleware` 同时管三件事：**给 Agent 文件工具**、**限制它能碰哪些文件**、**让它能看懂图片和 PDF 这类多模态内容**。这三件事看着分散，其实都围绕"文件"展开，放在一起理解最省事。

## 1. 文件工具与后端

![](https://picgo-1300696809.cos.ap-beijing.myqcloud.com/obsidian/1795850391213_file-backend.svg)

中间件通过 `wrap_tool_call` 提供一整套文件工具：

| 工具         | 作用             |
| ------------ | ---------------- |
| `ls`         | 列出目录         |
| `read_file`  | 读取文件         |
| `write_file` | 写入文件         |
| `edit_file`  | 编辑文件         |
| `glob`       | 按模式匹配文件   |
| `grep`       | 搜索文件内容     |
| `execute`    | 执行命令（可选） |

工具本身只是"动作"，真正的文件存在哪由 **backend（后端）** 决定。可以是本地文件系统，也可以是沙箱里的文件系统，还可以用 `CompositeBackend` 把不同路径路由到不同存储。把后端换成沙箱，Agent 就在隔离环境里干活，见 [[【沙箱】技术选型与 E2B 实战]]。

## 2. 文件操作权限

光给工具不够，还得限制范围。权限用 `FilesystemPermission` 声明：

```python
permissions = [
    # 禁止读取环境变量文件
    FilesystemPermission(
        operations=["read"],
        paths=["/home/user/workspace/.env", "/home/user/workspace/.env.*"],
        mode="deny",
    )
]

FilesystemMiddleware(
    _permissions=permissions,
)
```

每条规则三个配置项：

| 配置项       | 含义                                 | 可选值                                                                                  |
| ------------ | ------------------------------------ | --------------------------------------------------------------------------------------- |
| `operations` | 限制哪类操作                         | `read`：`ls`、`read_file`、`glob`、`grep`；`write`：`write_file`、`edit_file`、`delete` |
| `paths`      | 匹配的绝对路径，POSIX 风格 Glob 模式 | 如 `/home/user/workspace/**`                                                            |
| `mode`       | 匹配后怎么处理                       | `allow`、`deny`、`interrupt`                                                            |

`interrupt` 就是转到 [[【中间件】HITL 人工审批]] 那条路上，让人来决定。

### 2.1 匹配顺序：第一条匹配生效

这是最容易踩坑的地方。权限规则**按声明顺序匹配，第一条匹配的规则生效**；没有任何规则匹配时默认允许访问。

所以范围更具体的规则要写在前面：

```python
permissions = [
    # 先保护特殊文件
    FilesystemPermission(
        operations=["read"],
        paths=["/home/user/workspace/.env"],
        mode="deny",
    ),

    # 再允许整个工作目录
    FilesystemPermission(
        operations=["read", "write"],
        paths=["/home/user/workspace/**"],
        mode="allow",
    ),
]
```

把它想成安检名单：工作人员从上往下看，看到第一条符合的就照办，后面写什么都不看了。如果把 `allow /home/user/workspace/**` 放前面，读 `.env` 时会先命中 `allow`，后面的 `deny` 永远轮不上——这就是配置文件看着对、实际没拦住的原因。

### 2.2 execute 逃逸：为什么不能和沙箱后端直接组合

如果 `FilesystemMiddleware` 提供了 `execute` 工具，模型可以完全绕过文件工具的权限检查：Shell 里一条 `cat`、`cp`、`rm` 就能读写任何文件，文件工具那一层规则形同虚设。

因此当前版本**不允许**把权限规则和沙箱后端直接配在一起：

```python
create_deep_agent(
    backend=sandbox_backend,
    permissions=permissions,
)
```

这样创建 Agent 会抛 `NotImplementedError`。

正确做法是：**在沙箱这一层建立文件系统隔离**（容器/微虚拟机的边界），再用 `interrupt_on` 控制高风险工具的审批。也就是说，权限要么在文件工具层管，要么在沙箱层管，不要以为叠在一起就更安全——详见 [[沙箱权限与安全执行]]。

## 3. 多模态消息

![](https://picgo-1300696809.cos.ap-beijing.myqcloud.com/obsidian/1795850391214_多模态消息.svg)

多模态消息主要出现在 `ToolMessage` 和 `HumanMessage` 里（`AIMessage` 没有特殊处理，系统消息几乎不会遇到）。核心有两个问题：

**格式问题**：工具节点读到一张图片或 PDF 后，得把它构造成一条格式正确的多模态消息，而不是把二进制硬塞进文本。

**能力问题**：不是所有模型都支持多模态。遇到不支持的模型，要把这些消息重排或拿掉，否则请求直接报错。

这两件事 Deep Agent 已经通过 `FilesystemMiddleware` 自动处理好了：

- 工具节点用 `wrap_tool_call` 返回针对性的 `ToolMessage`，把文件变成标准消息块。
- 模型节点用 `wrap_model_call` 拦截消息里的文件块，按模型能力决定给不给。

![工具节点产出的多模态消息](https://picgo-1300696809.cos.ap-beijing.myqcloud.com/obsidian/1795850391751_202608281302604.svg)

判断依据是模型对象的 `profile` 属性：

```python
profile = {
    # 是否支持对应输入类型
    "image_inputs": True,
    "pdf_inputs": True,
    "audio_inputs": False,
    "video_inputs": False,

    # 是否允许媒体出现在工具结果 ToolMessage 中
    "image_tool_message": False,
    "pdf_tool_message": True,
}
# 没有声明的字段默认表示支持
```

前四个字段决定"模型能不能看懂这类媒体"，后两个决定"媒体能不能放在工具结果里，而不是只能放在用户消息里"。比如 `image_tool_message: False` 表示图片不能直接塞进 `ToolMessage`，中间件就得换个位置放。这套按能力裁剪消息的做法，是 [[【基础】模型接入与消息体系]] 里消息体系的延伸。
