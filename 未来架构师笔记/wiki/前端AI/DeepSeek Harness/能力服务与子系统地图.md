DeepSeek Harness 里有一个核心概念：capability seam。这里用中文叫**能力服务**。

先不用纠结英文名。它的意思是：把一个能力拆成“接口、实现、使用者”三部分，让系统可以换实现而不改使用者。

## 1. 能力服务的三层

一个完整能力通常有三层：

| 层         | 英文名             | 大白话解释                       |
| ---------- | ------------------ | -------------------------------- |
| 服务定义   | Service Definition | 规定这个能力长什么样、有哪些方法 |
| 服务提供方 | Service Provider   | 真正实现这个能力                 |
| 消费方     | Consumer           | 使用这个能力的插件或工具         |

举个文件系统能力的例子：

```text
服务定义：文件系统应该支持读、写、编辑、观察文件
提供方 A：本地文件系统实现
提供方 B：远程沙箱文件系统实现
消费方：面向模型的文件读取/编辑工具
```

消费方只依赖服务定义，不直接绑死某个提供方。这样以后从本地执行换到远程沙箱，工具层可以少改甚至不改。

## 2. 为什么单独一个 Provider 不算完整能力

如果只有“实现”，没有统一接口和消费方，那只是一个模块，不是能力服务。

完整能力要同时回答三个问题：

1. 这个能力对外承诺什么接口？
2. 谁来实现这个接口？
3. 哪些地方通过这个接口使用能力？

DeepSeek Harness 重视这个拆分，是因为 Agent 的能力会不断增长。如果每个工具都直接接触具体实现，系统很快会变成一团耦合代码。

## 3. 主要子系统分组

官方子系统很多，可以先按职责分成几大类：

| 分组         | 代表子系统                                   | 负责什么                         |
| ------------ | -------------------------------------------- | -------------------------------- |
| 内核与作用域 | core、scope、invariants                      | Agent 循环、作用域、运行时不变式 |
| 会话与持久化 | session、persistence、session-query          | 记录和查询会话事件               |
| 模型与上下文 | llm-streaming、system-prompt、compaction     | 模型消息、系统提示词、上下文压缩 |
| 执行与工具   | tools、shell、filesystem、terminal、subagent | 让模型能调用外部能力             |
| 策略与交互   | approval、sandbox、permission-presets、plan  | 审批、安全、权限、计划模式       |
| 平台与接入   | web-server、typert、client-modules、settings | Web、远程调用、用户设置等        |

这些不是互相孤立的。比如一次 shell 工具调用，会同时经过 tools、approval、sandbox、subprocess、session 等多个子系统。

## 4. ctx 服务就是子系统的入口

DeepSeek Harness 里很多子系统最终会暴露成 `ctx.*` 服务：

| ctx 服务           | 能力               |
| ------------------ | ------------------ |
| `ctx.sessions`     | 会话存储和事件日志 |
| `ctx.llm`          | 模型适配器注册表   |
| `ctx.tools`        | 工具注册和工具执行 |
| `ctx.systemPrompt` | 系统提示词组装     |
| `ctx.sandbox`      | 进程沙箱           |
| `ctx.approval`     | 一次性审批         |
| `ctx.skills`       | 技能发现和加载     |
| `ctx.subagents`    | 子代理启动和委派   |
| `ctx.web`          | Web 搜索和抓取     |

你可以把 `ctx` 当成系统总服务台。插件不需要知道每个能力内部怎么实现，只要拿到对应服务就能协作。

## 5. ctx 上的不一定都是内置服务

`ctx.*` 上的服务有些来自框架内置能力，有些来自 DeepSeek Harness 自己的插件，也可以来自你写的插件。

关键不在于“是不是内置”，而在于：有没有一个插件负责提供这个服务。提供服务的插件启动成功后，`ctx` 上才会出现对应入口。

```text
插件 X 提供 searchIndex 服务
  -> ctx.searchIndex 可用

插件 Y 需要 searchIndex 服务
  -> inject = ['searchIndex']
  -> apply(ctx) 里调用 ctx.searchIndex
```

所以 `ctx` 不是只放官方内置能力的地方，它更像一个共享平台。只要服务设计清楚，你自己的插件也可以把新能力放到 `ctx` 上。

## 6. 服务不一定都是给模型直接用的

很多人第一次看 Agent 框架，会以为 `ctx.tools`、`ctx.llm`、`ctx.sessions` 都是“给 AI 用的”。这个说法只对了一部分。

更准确的分法是：

| 服务类型     | 例子                            | 谁主要使用                        |
| ------------ | ------------------------------- | --------------------------------- |
| 模型直接相关 | `ctx.tools`、`ctx.systemPrompt` | 模型通过工具描述和上下文间接使用  |
| 运行时能力   | `ctx.llm`、`ctx.sessions`       | Agent 循环、CLI、Web UI、插件代码 |
| 策略能力     | `ctx.approval`、`ctx.sandbox`   | 工具执行流水线和权限控制逻辑      |
| 平台能力     | `ctx.settings`、`ctx.commands`  | 人、界面、命令行和其他插件        |

模型通常不是直接拿到 `ctx` 对象。模型看到的是系统组装后的消息、工具 schema、工具结果和上下文。真正直接调用 `ctx.xxx` 的，是 DeepSeek Harness 的运行时代码和插件代码。

人要使用这些能力，通常也不是打开 `ctx` 手动调用，而是通过 Web UI、CLI、配置文件、自动化协议或你写的插件间接使用。

## 7. 注册到服务里的不是插件

一个插件可以把东西注册到某个服务里，但注册进去的东西通常叫“条目”，不是另一个服务，也不是自动变成 `ctx.tools.A`。

以 `ctx.tools` 为例：

```text
ctx.tools 是工具服务
  - 工具 A 是注册进去的一个工具条目
  - 工具 B 是注册进去的一个工具条目
  - 工具 C 是注册进去的一个工具条目
```

其他插件如果想使用工具服务，依赖的是：

```ts
export const inject = ['tools']
```

然后怎么查工具、执行工具、列出工具，要看 `ctx.tools` 这个服务自己提供了哪些 API。一般不要想象成：

```ts
ctx.tools.A
ctx.tools.B
```

更合理的心智模型是：`ctx.tools` 是一个注册表和执行器，里面保存了很多工具定义；模型看到工具 schema 后发起工具调用，工具服务再按名字找到对应条目并执行。

这点对其他服务也一样：注册到 `ctx.llm` 的可能是模型适配器，注册到 `ctx.systemPrompt` 的可能是提示词片段，注册到 `ctx.commands` 的可能是命令。具体怎么注册、怎么查询、怎么执行，由每个服务自己的 API 决定。

## 8. 一次工具调用会经过哪些能力

以“模型想运行一个命令”为例：

```text
模型输出工具调用
  -> ctx.tools 接收并走工具流水线
  -> ctx.approval 可能询问用户是否允许
  -> ctx.sandbox 计算文件写入边界
  -> ctx.shell 或 ctx.subprocess 执行命令
  -> ctx.sessions 记录 tool/call 和 tool/result
  -> UI 从会话事件和工具展示信息渲染卡片
```

这就是能力服务的价值：每个子系统只负责自己的部分，通过清晰接口接起来。

## 9. 为什么这对 Agent 很重要

Agent 系统的问题不是“模型能不能回答”，而是“模型要行动时，系统能不能管住行动”。

能力服务让 DeepSeek Harness 可以做到：

- 工具和策略分离。
- 本地实现和远程实现可替换。
- UI、CLI、自动化协议可以共享底层能力。
- 子系统失败时更容易定位是哪一层的问题。
- 新能力加入时不用大改 Agent 循环。

这就是它和简单 SDK 的区别：SDK 通常只帮你调用模型；Harness 要管理模型行动所需的整个环境。
