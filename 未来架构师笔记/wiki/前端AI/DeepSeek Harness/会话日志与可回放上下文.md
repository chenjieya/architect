DeepSeek Harness 的会话日志可以理解成一本**只追加、不涂改的工作记录本**。

用户说了什么、模型回了什么、模型调用了哪个工具、工具返回了什么，都按顺序写进这本记录本。系统后面要恢复、回放、展示、继续对话，都从这本记录本推导。

## 1. 什么叫“唯一真源”

唯一真源的意思是：系统相信日志，而不是相信某个临时变量。

普通聊天程序可能会维护一个 `messages` 数组：

```text
messages = [
  用户消息,
  模型消息,
  工具结果
]
```

这样很简单，但问题是：如果中间还要记录流式片段、工具卡片、用量、错误、恢复点、压缩摘要，这个数组就不够用了。

DeepSeek Harness 选择记录更底层的事件：

```text
turn/start
user/message
assistant/chunk
assistant/message
tool/call
tool/result
step/end
turn/end
```

然后再从这些事件派生出模型需要的消息历史。这样日志更像数据库里的交易流水，而不是临时聊天数组。

## 2. 为什么日志只能追加

只追加的意思是：新事实来了就加一条，不回头修改旧事实。

这有几个好处：

- 可以知道事情发生的准确顺序。
- 出错后可以定位是哪一步出错。
- UI 可以按事件重放整个过程。
- 持久化后可以恢复会话。
- 插件可以扩展新的事件类型，而不破坏旧事件。

比如工具调用不是只存“最终答案”，而是分成：

```text
tool/call：模型要求调用哪个工具，参数是什么
tool/result：工具最终返回给模型的结果是什么
```

这让系统能区分“模型想做什么”和“工具实际做成了什么”。

## 3. 模型可见即已记录

DeepSeek Harness 有一个很关键的原则：**只要某个内容会进入模型请求，就必须能从会话日志重建。**

这句话非常重要。

如果模型看到了一段隐藏在内存里的上下文，但日志里没有记录，后面就会出现问题：

- 会话恢复后，模型历史变了。
- 调试时不知道模型为什么做出某个判断。
- 压缩、fork、回放无法准确复现。
- UI 展示和模型真实输入对不上。

所以，新增模型可见输入时，不能只是“临时塞进 prompt”。正确做法是新增或复用会话事件，让它成为日志的一部分。

## 4. assistant/chunk 和 assistant/message 的区别

模型流式输出时，会一点点吐出内容。DeepSeek Harness 会记录原始流式片段，也会记录组装后的完整消息。

| 事件                | 含义                 | 主要用途               |
| ------------------- | -------------------- | ---------------------- |
| `assistant/chunk`   | 原始流式片段         | UI 实时展示、精确回放  |
| `assistant/message` | 组装后的完整模型消息 | 派生模型历史、继续对话 |

这就像录视频和写摘要：chunk 是每一帧，message 是最后剪好的完整片段。两者都重要。

## 5. 工具结果为什么也要进日志

工具结果会影响模型下一步怎么回答，所以它属于模型可见上下文。

例如模型调用文件搜索工具，工具返回“找到了 12 个测试文件”。下一次模型请求会把这个结果交给模型。如果日志里没有 `tool/result`，恢复会话时模型就不知道当时工具返回过什么。

因此 [[工具调用与执行流水线]] 的最终产物必须进入会话日志，而不是只在工具函数返回值里存在。

## 6. 日志和上下文压缩的关系

上下文太长时，系统可能需要压缩历史。压缩不是随便删消息，而是基于日志选择哪些内容保留、哪些内容总结。

因为原始日志在，系统可以：

- 精确知道每段上下文来自哪里。
- 在压缩后记录摘要事件。
- 后续仍能解释“模型现在看到的是哪一版历史”。

所以日志是压缩、恢复、fork、查询、标题、遥测等能力的共同地基。

## 7. 最小心智模型

记住下面这句话就够了：

```text
DeepSeek Harness 不是把聊天历史存在一个 messages 数组里，
而是把整个 Agent 工作过程写成事件日志，
再从日志里推导模型需要看的内容。
```

这也是它比普通调用 SDK 更工程化的地方。
