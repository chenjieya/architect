工具调用是 Agent 和普通聊天机器人最大的区别之一。

普通聊天机器人只能“说”。Agent 可以“做”：查文件、跑命令、搜索网页、创建待办、启动子代理。DeepSeek Harness 的工具系统就是负责把模型说的“我要调用工具”变成一次受控执行。

## 1. 工具不是普通函数

在 DeepSeek Harness 里，一个工具不只是一个 `execute()` 函数。它还包含：

| 部分                            | 作用                          |
| ------------------------------- | ----------------------------- |
| `name`                          | 工具名，模型用它发起调用      |
| `description`                   | 告诉模型这个工具什么时候该用  |
| `parameters`                    | 参数 schema，告诉模型该传什么 |
| `output.schema`                 | 工具真实返回值的规范          |
| `output.render`                 | 把工具返回值转成模型可读内容  |
| `execute`                       | 真正执行工具逻辑              |
| `presentCall` / `presentResult` | UI 怎么展示工具调用卡片       |

所以工具是一个“协议对象”，不是随便暴露一个函数给模型。

## 2. 为什么需要参数和输出校验

模型生成的工具参数本质上是一段 JSON。模型可能写错字段、漏字段、类型不对。

如果工具直接相信模型，就容易出问题。比如工具需要：

```json
{ "name": "Ada" }
```

模型却传：

```json
{ "username": 123 }
```

这时工具不能假装没事。DeepSeek Harness 用 schema 检查参数，也检查工具执行后的输出是否符合声明。

这带来两个好处：

- 模型输入错了，可以走统一错误路径。
- 工具自己返回错了，也能在系统边界被发现。

## 3. 工具执行流水线

一次工具调用不是直接进入 `execute()`，而是经过流水线：

```text
模型产生 tool-call
  -> 写入 tool/call 日志
  -> tools/pre-execute
  -> 权限、审批、沙箱等守卫
  -> tools/execute
  -> 工具 execute()
  -> tools/post-execute
  -> output.render / finalizeContent
  -> tools/result
  -> 写入 tool/result 日志
```

这条流水线的意义是：工具能力和策略能力分开。

例如文件编辑工具只负责“怎么编辑文件”；审批插件负责“这次编辑要不要问用户”；沙箱插件负责“进程能不能写出工作区”。它们通过同一条流水线协作。

## 4. pre-execute、execute、post-execute 分别干什么

| 阶段                 | 主要职责                         | 类比         |
| -------------------- | -------------------------------- | ------------ |
| `tools/pre-execute`  | 执行前决策：允许、拒绝、询问用户 | 门卫检查     |
| 单调守卫             | 不允许后面的策略推翻更严格的拒绝 | 安全红线     |
| `tools/execute`      | 包装真正执行：超时、重试、指标   | 外层执行环境 |
| 工具 `execute()`     | 工具自己的业务逻辑               | 真正干活     |
| `tools/post-execute` | 检查、替换、追加上下文           | 质检         |
| `tools/result`       | 观察最终不可变结果               | 盖章归档     |

“单调守卫”可以简单理解成：安全策略不能越走越宽松。一旦有必须拒绝的原因，后面不能随便改成允许。

## 5. 为什么工具结果要渲染

工具内部返回的规范值，未必适合直接塞给模型。

例如文件搜索工具内部可能返回结构化 JSON：

```json
{
  "matches": [{ "path": "src/app.ts", "line": 12 }]
}
```

但模型更适合看到一段整理好的内容块。`output.render` 就负责把“工具内部结果”投影成“模型可读结果”。

这样做可以同时满足：

- 工具内部结果结构稳定。
- 模型看到的内容清楚。
- UI 可以用自己的方式展示。

## 6. 和 Function Calling 的关系

[[【LLM】Function Calling]] 讲的是模型厂商层面的“模型如何表达我要调用函数”。DeepSeek Harness 的工具系统则是工程层面的“收到这个调用后，怎么安全、可靠、可回放地执行”。

可以这样区分：

```text
Function Calling：模型输出 tool-call 的协议
DeepSeek Harness 工具流水线：tool-call 进入真实系统后的执行治理
```

## 7. 最小例子

官方入门文档里的 `greet` 工具很简单：

```ts
ctx.tools.register(
  defineTool({
    name: 'greet',
    description: 'Greet someone by name.',
    parameters: {
      name: {
        type: 'string',
        required: true,
        description: 'The name to greet',
      },
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args) {
      return `Hello, ${args.name}!`
    },
  }),
)
```

这段代码背后已经包含了参数描述、参数校验、输出声明、输出渲染和工具注册。真正的生产工具会再叠加审批、沙箱、超时、UI 展示和日志记录。

## 8. 记住这个原则

工具越强，风险越高。能读文件、写文件、跑命令的工具尤其如此。

所以 DeepSeek Harness 不让模型“直接执行函数”，而是让工具调用经过一条可扩展、可审计、可拦截的流水线。
