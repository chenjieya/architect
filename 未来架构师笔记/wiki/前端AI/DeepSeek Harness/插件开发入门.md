理解 DeepSeek Harness 插件开发，可以先抓住三个动作：

1. 写一个插件模块。
2. 通过 `ctx` 注册能力。
3. 通过 patch 把插件挂到运行中的 profile 上。

这篇只讲入门心智模型，不追求覆盖所有 API。

## 1. 最小插件长什么样

最小插件就是一个导出 `apply(ctx)` 的 TypeScript 模块：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  console.log('[hello-plugin] plugin loaded!')
}
```

这里的关键是 `ctx`。插件不是直接改主程序，而是通过 `ctx` 和系统协作。后面注册工具、监听事件、提供服务，都从 `ctx` 开始。

## 2. 怎么把插件挂进去

官方入门方式是写一个 patch：

```yaml
- insert:
    - id: hello
      name: '/absolute/path/to/deepseek-harness/scratch-plugin/src/my-plugin.ts'
```

然后启动：

```sh
pnpm dsh web --patch ./scratch-plugin/cordis.yml
```

这和 [[Profile 与组合包]] 的关系是：profile 给出默认插件树，patch 在最后叠上你的本地插件。

## 3. 注册工具

如果插件要添加一个模型可调用的工具，需要依赖 `tools` 服务：

```ts
export const inject = ['tools']
```

然后在 `apply(ctx)` 里注册：

```ts
ctx.tools.register(
  defineTool({
    name: 'greet',
    description: 'Greet someone by name.',
    parameters: {
      name: {
        type: 'string',
        required: true,
        description: 'The name to greet',
      },
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args) {
      return `Hello, ${args.name}!`
    },
  }),
)
```

这段代码说明了 [[工具调用与执行流水线]] 的基础：模型看到的是 `name`、`description`、`parameters`；真正执行时才会进入 `execute()`，输出再通过 `render` 转成模型可读内容。

## 4. 注册到已有服务，还是自己提供服务

写插件时，先判断你要做的是哪一种事：

| 你要做什么         | 常见写法                         | 大白话理解                   |
| ------------------ | -------------------------------- | ---------------------------- |
| 使用已有能力       | `inject = ['tools']` 后调用服务  | 我需要别人已经提供好的服务   |
| 往已有服务添加条目 | 调用 `ctx.tools.register(...)`   | 我把一个工具放进工具注册表   |
| 提供一个新服务     | 写 `Service` 子类并挂到 `ctx` 上 | 我给共享平台新增一个能力入口 |

比如你只是想新增一个工具，通常不需要自己提供服务，只要依赖 `tools` 服务，然后向它注册工具条目。

如果你要做一个“搜索索引能力”，并且希望很多插件都能直接调用它，那就更适合提供一个新服务，例如：

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

export class SearchIndexService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'searchIndex')
  }

  async query(keyword: string) {
    return []
  }
}

export function apply(ctx: Context) {
  new SearchIndexService(ctx)
}
```

这样其他插件就可以声明：

```ts
export const inject = ['searchIndex']
```

然后在 `apply(ctx)` 里使用 `ctx.searchIndex.query(...)`。这时插件之间的真实依赖关系就很清楚：不是 A 依赖 B 的文件，而是 A 依赖 B 提供出来的 `searchIndex` 服务。

## 5. 每个服务的注册方法不一定都叫 register

`apply(ctx)` 的本质是：插件启动时，拿到共享上下文，然后调用对应服务的 API。

但不同服务负责的事不一样，所以注册方法不一定统一叫 `register`：

| 服务               | 可能的调用方式   | 原因                         |
| ------------------ | ---------------- | ---------------------------- |
| `ctx.tools`        | 注册工具定义     | 工具服务管理工具条目         |
| `ctx.llm`          | 注册模型适配器   | 模型服务管理不同模型提供方   |
| `ctx.systemPrompt` | 注册提示词片段   | 提示词服务负责组装上下文     |
| `ctx.commands`     | 注册命令         | 命令服务面向 CLI 或界面动作  |
| `ctx.on`           | 监听事件         | 事件不属于某个单一注册表条目 |
| `ctx.effect`       | 安装可清理副作用 | 用于卸载时自动回收资源       |

因此不能死记“所有服务都是 `register`”。要看这个服务本身的文档和类型定义。服务就像一个小子系统，它自己决定怎么注册、怎么查询、怎么执行、卸载时怎么清理。

## 6. 配置不要硬编码

DeepSeek Harness 的插件约定是：不同部署可能不同的值，要做成配置，而不是写死在代码里。

例如不要这样：

```ts
const TIMEOUT = 30000
```

更好的方式是定义 `Config`：

```ts
import Schema from '@deepseek-ai/schemastery'

export interface Config {
  timeoutMs: number
}

export const Config: Schema<Config> = Schema.object({
  timeoutMs: Schema.number().default(30000),
})
```

这样用户可以在 `cordis.yml` 里改配置，而不是改源码。

## 7. 配置错误要尽早失败

配置 schema 的意义不只是补默认值，还要在插件加载时发现错误。

如果 `apiKey` 必填，就用 schema 标出来；如果 `mode` 只能是几个固定值，也用 schema 限制。这样错误会在启动时暴露，而不是运行到一半才出奇怪问题。

## 8. 自动清理

插件通过 `ctx` 注册的资源，在插件卸载时会被清理。比如事件监听、工具注册、定时器都应该绑定到 effect。

```ts
export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setInterval(() => {
      console.log('heartbeat')
    }, 5000)

    return () => clearInterval(timer)
  })
}
```

这和 [[插件化架构与 Cordis]] 里的“可逆副作用”是一回事：插件不应该在系统里留下清不掉的旧资源。

## 9. 小白学习路径

如果你想真正动手，可以按这个顺序：

1. 写一个只打印日志的插件，确认能被 patch 加载。
2. 加 `inject = ['tools']`，注册一个简单工具。
3. 给工具加参数 schema 和输出 schema。
4. 分清自己是在使用已有服务、注册条目，还是提供新服务。
5. 把硬编码值改成 `Config`。
6. 再学习服务、事件和能力分层。

不要一开始就写复杂工具。先弄明白“插件如何进入系统、如何通过 `ctx` 注册能力、如何被卸载清理”，后面才不容易乱。
