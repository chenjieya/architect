Agent 一旦能运行命令、改文件、访问网络，就必须考虑安全。

DeepSeek Harness 的沙箱、审批和权限预设，就是为了回答一个问题：**模型想做某件事时，系统到底允许它碰哪里、写哪里、执行到什么程度？**

## 1. 为什么不能让工具直接裸跑

如果模型调用了一个 shell 工具，最危险的情况是工具直接在你的电脑上运行任意命令。

这样会有几个问题：

- 模型可能误删文件。
- 工具可能写到工作区之外。
- 插件可能把权限判断写漏。
- 不同平台的限制方式不一样，工具很难自己处理。

所以 DeepSeek Harness 把执行能力放进 [[工具调用与执行流水线]]，再由沙箱和审批等策略统一治理。

## 2. 三种沙箱模式

官方沙箱文档里有三个模式：

| 模式                 | 含义                       | 适合场景                   |
| -------------------- | -------------------------- | -------------------------- |
| `read-only`          | 尽量只读，不允许写文件     | 查看、搜索、分析           |
| `workspace-write`    | 允许写当前工作区和临时目录 | 修改项目代码               |
| `danger-full-access` | 绕过隔离，直接执行         | 用户明确信任且需要完整权限 |

注意：这些模式主要管的是**文件系统效果**，也就是能不能写文件、写到哪里。网络和进程可见性不是这个词汇本身承诺的范围。

## 3. workspace-write 为什么重要

对编程 Agent 来说，最常见的合理权限是 `workspace-write`。

它允许 Agent 修改当前项目，但不应该随便写到你的用户目录、系统目录或其他项目目录。

大白话就是：

```text
你可以在这张办公桌上写字、改文件，
但不能跑去翻我的抽屉、改别的项目。
```

这让 Agent 能完成开发任务，同时把影响范围限制在工作区内。

## 4. 审批和沙箱不是一回事

审批回答的是：**这次操作用户同不同意？**

沙箱回答的是：**即使同意了，进程实际能碰到哪里？**

两者都需要。

例如模型想执行一个写文件命令：

```text
tools/pre-execute
  -> 判断这类操作需要审批
  -> 用户允许
  -> 解析 sandbox policy
  -> 用 workspace-write 包装 argv
  -> 真正 spawn 进程
```

如果只有审批，没有沙箱，用户点错一次就可能放大风险。如果只有沙箱，没有审批，用户不知道 Agent 正在做什么。

## 5. partial enforcement 是什么

官方文档提到沙箱后端会报告强制执行完整性：

| 状态      | 含义                               |
| --------- | ---------------------------------- |
| `full`    | 后端完整管住了该模式承诺的文件效果 |
| `partial` | 由于平台或内核限制，只能管住一部分 |

这不是小细节。比如某些旧内核或 Windows ACL 场景下，沙箱可能无法给出完全保证。此时要求绝对边界的调用方应该拒绝执行或把风险暴露出来，而不是假装安全。

## 6. 为什么策略要逐调用解析

DeepSeek Harness 的沙箱策略不是固定在提供方上的，而是每次能力调用时解析。

这意味着：

- 一个只读查询可以用 `read-only`。
- 一个代码修改可以用 `workspace-write`。
- 一次用户批准的重试可以临时使用更宽权限。
- 不同会话可以同时使用不同边界。

这比“整个程序启动时固定一个权限”更灵活，也更适合 Agent 场景。

## 7. 最小心智模型

可以把 DeepSeek Harness 的安全执行想成三道门：

```text
第一道门：工具流水线，判断这次调用是否进入执行阶段
第二道门：审批和权限策略，判断用户是否允许、权限应多大
第三道门：沙箱后端，把命令包进实际约束里运行
```

对小白来说，先记住：**Agent 能做事很强，但越强越需要边界。沙箱就是给 Agent 行动划边界的工程机制。**
