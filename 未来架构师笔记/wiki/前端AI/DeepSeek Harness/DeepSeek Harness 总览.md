DeepSeek Harness 可以先理解成一个**专门运行 Agent 的工程底座**。

如果只写一个普通聊天机器人，代码通常是：用户发消息，程序调用大模型，大模型回一段文字。但真正的 Agent 不止聊天，它还要读文件、改文件、运行命令、调用工具、记录上下文、处理权限、恢复会话、展示界面。DeepSeek Harness 做的就是把这些通用能力整理成一套可以复用、可以替换、可以扩展的系统。

## 1. 一句话理解

DeepSeek Harness 不是单个模型，也不是一个普通 SDK，而是一套 Agent 运行框架。

它的核心目标是：

- 让模型能稳定地调用工具。
- 让每次对话和工具结果都能被记录、回放和恢复。
- 让文件系统、终端、网页搜索、子代理等能力可以按需接入。
- 让安全策略、审批、沙箱这类规则不要散落在每个工具里。
- 让 Web UI、命令行、自动化协议都能复用同一套 Agent 内核。

可以把它想成一座工作台：模型是坐在工作台前的人，工具是桌上的锤子、螺丝刀、电脑；会话日志是工作记录本；沙箱和审批是安全管理员；插件系统负责决定这张桌子上到底放哪些工具。

## 2. 它解决什么问题

没有 Harness 时，开发 Agent 往往会把很多事情混在一起：

| 问题            | 直接写 Agent 容易怎样                      | DeepSeek Harness 的处理方式  |
| --------------- | ------------------------------------------ | ---------------------------- |
| 工具太多        | 每个工具各写各的调用和校验                 | 统一注册到工具系统           |
| 上下文混乱      | 历史消息、工具结果、系统提示词散落在内存里 | 统一从会话日志派生           |
| 安全难控        | 工具自己决定能不能写文件、跑命令           | 统一走审批、权限、沙箱       |
| 扩展困难        | 改核心代码才能加能力                       | 通过插件挂载能力             |
| UI 和运行时耦合 | 界面逻辑和 Agent 循环互相缠住              | UI 消费事件和投影结果        |
| 调试困难        | 不知道模型到底看到了什么                   | 模型可见内容必须可从日志重建 |

所以它更像“Agent 操作系统”：上层业务不用每次重新造工具调度、会话存储、权限控制这些基础设施。

## 4. 最小运行画面

一次最典型的流程可以这样理解：

```text
用户输入
  -> Agent 领取输入
  -> 组装系统提示词和工具列表
  -> 调用大模型
  -> 大模型输出文字或工具调用
  -> 工具流水线检查权限并执行
  -> 工具结果写回会话日志
  -> 如果还需要模型总结，就进入下一步
  -> 轮次结束
```

这里的关键不是“调用模型”这一步，而是前后所有工程环节：怎么决定模型能看什么、能用什么工具、工具能不能执行、执行结果怎么记录、界面怎么展示。

## 5. 学习顺序

如果你是第一次接触这套系统，可以按下面顺序读：

1. 先读本文，建立全局图。
2. 读 [[插件化架构与 Cordis]]，理解“为什么一切皆插件”。
3. 读 [[Profile 与组合包]]，理解启动时怎么拼出一个 Agent。
4. 读 [[Agent 轮次与步骤生命周期]]，理解一次对话如何跑完。
5. 读 [[会话日志与可回放上下文]]，理解为什么日志是核心。
6. 读 [[模型消息与流式输出]]，理解模型回复如何被拆成内容块和流式片段。
7. 读 [[工具调用与执行流水线]] 和 [[沙箱权限与安全执行]]，理解工具为什么不能直接裸跑。
8. 读 [[插件开发入门]]，开始把概念落到代码。

DeepSeek Harness 的难点不是某一个 API，而是它把 Agent 拆成很多可替换部件。只要抓住“插件贡献服务，事件连接流程，日志保证回放，流水线保护工具执行”这四件事，后面的细节就能慢慢挂上去。
