[[【基础】词元]] 讲了怎么把文字切成 token，[[【基础】Token统计]] 讲了怎么数 token。但 token 现在还是一串**编号**（如 `[33256, 11789]`）——模型根本"看不懂"这些数字背后的含义。这一讲就解决：**怎么让一个 token 带上"意思"**。答案是**词嵌入（Word Embedding）**，它也是 Transformer 前向传播的**第一个阶段**。

## 1. 一句话理解

**词嵌入 = 把一个 token 变成一个"多维数字向量"，用向量在空间里的位置来表达这个词的含义。**

## 2. 为什么不能直接用 Token ID

在预处理阶段，分词器（见 [[【基础】词元]]）已经把文字变成了 Token ID 序列。但这串 ID **不能直接拿去训练**，根源有两个：

### 2.1 Token ID 无法表示语义

Token ID 只是一个"文字符号的编号"，仅靠一个数字无法表达它背后丰富的语义。比如，你知道 `كِتاب` 这个 token 是什么含义吗？单看编号，机器也不知道。

### 2.2 Token ID 无法表达语义之间的数学关系

假设"吃苹果"对应 token 序列 `[33256, 11789]`，请问 `33256 + 11789` 是什么意思？答案是——**没有意义**。两个编号相加得不出任何语义。

> 大白话：Token ID 只是"门牌号"，门牌号之间做加减法毫无意义。**要表达语义、还要能运算，就需要更多维度来描述一个 token。**

## 3. Token ID 的真正作用：查表的钥匙

第 2 节说 Token ID"不能直接用"，但你可能会疑惑：既然没用，为什么还要切 token、编 ID？其实 Token ID **有大用**——它的角色是**索引（index）**，是"查表的钥匙"，而不是"参与计算的数值"。

### 3.1 完整流程：Token ID 只是第一站

真正的处理链条是这样：

```
文本 → 分词器 → Token ID 序列 → 查嵌入表 → 向量序列（张量）→ 喂给模型
```

- 分词器把文字切成 token（见 [[【基础】词元]]），并给每个 token 编一个 ID。
- **Token ID 自己不参与计算**，它只是告诉模型："去嵌入表里**第 33256 行**，把那行向量取出来给我。"
- 模型真正读的是查出来的**向量**。把这一批 token 查出的向量拼在一起，就得到形状为 $(序列长度, 嵌入维度)$ 的**张量**——这才是真正喂给 Transformer 的东西。

> 大白话：Token ID 像字典里的**页码**。你报页码（Token ID），查字典（嵌入表），真正被读的是那一页上的字（向量）。页码自己没内容，但它是找到内容的地址。

### 3.2 嵌入表（Embedding Matrix）：一张可查询的大表

"查表"查的是一张叫**嵌入矩阵（Embedding Matrix）**的表：

| 行（= Token ID） | 向量内容                                |
| ---------------- | --------------------------------------- |
| 0                | $[0.02, -0.11, 0.35, \dots]$            |
| 1                | $[0.88, 0.14, -0.03, \dots]$            |
| 2                | $[0.21, 0.77, 0.08, \dots]$             |
| $\dots$          | $\dots$                                 |
| **33256**        | $[\dots]$ ← 报告"苹果"的 ID，就取这一行 |
| $\dots$          | $\dots$                                 |

- **行数** = 词表大小（有多少个 token）。
- **列数** = 嵌入维度（每行向量多长）。
- 所以"把 Token ID 变成向量"这句话的精确含义 = "**用 Token ID 当行号，从嵌入矩阵里取出一行**"。

### 3.3 为什么不能把 Token ID 直接当数值算

既然 Token ID 只是行号，就更清楚为什么不能拿它当数值：

- `33256` 和 `33257` 相邻，**不代表**"苹果"和"下一个词"语义相近——编号是随意排的。
- 如果直接拿 `33256` 这个整数去算，模型会以为"编号相近 = 语义相近"，学到一堆假规律。
- 而嵌入矩阵里的向量，值是**训练出来的**（见第 6 节"谁来填这些值"），所以向量之间的远近才真实反映语义。

> 大白话：**门牌号按顺序排，但语义不按顺序排**。3 号门牌和 4 号门牌相邻，不代表 3 户人家和 4 户人家是邻居。所以不能拿门牌号本身做算术，只能拿它去查地址（向量）。

### 3.4 一句话记住

**Token ID 是"索引/查表钥匙"，嵌入向量才是"内容"；模型训练真正吃的是张量，Token ID 只是取张量的第一步。**

## 4. 用向量描述 Token

既然一个数字不够，就用**多个数字**（一个向量）来描述一个 token。

比如"苹果"这个词，可以从多个角度描述：

| 维度   | 含义           | 苹果的值 |
| ------ | -------------- | -------- |
| 维度 1 | 可被食用的程度 | 0.9      |
| 维度 2 | 科技程度       | 0.6      |
| 维度 3 | 消费水平       | 0.5      |

于是"苹果" = 向量 `[0.9, 0.6, 0.5]`。

假设另一个 token 的值是 `[0.7, 0.8, 0.3]`，把它俩放到三维空间里，**位置比较接近**——这就在几何上表达了"语义相近"。向量可视化可以看 [TensorFlow Embedding Projector](https://projector.tensorflow.org/)。

下图就是 Embedding Projector 的可视化效果：每个点是一个词的向量，**语义相近的词会聚成一团**（比如数字、颜色、国家各自扎堆）。

![词向量可视化：相似词在空间中聚在一起](https://picgo-1300696809.cos.ap-beijing.myqcloud.com/20260823195833809.png)

> 大白话：一个数字不够，就用"一列数字"（向量）来描述一个词。**语义相近的词，向量在空间里靠得近；语义不相关的词，离得远**。这正是 [[【LLM】嵌入]] 里"小猫/小狗向量接近"同一个道理。

## 5. 向量带来的神奇数学关系

当 token 变成向量后，它们之间能"做运算"，产生一些惊人的规律：

- $苹果 \approx Apple$
- $国王 - 王后 \approx 男人 - 女人$
- $男人 + 医生 \approx 男医生$
- $2 \times 开心 \approx 狂喜$

这些式子说明：**向量不仅表达了语义，还把语义关系"编码"成了几何关系**——"国王−王后"这个方向，和"男人−女人"这个方向是同一个方向（都指向"性别"）。

> 大白话：把词变成向量后，"词的加减法"开始有含义了——"国王"去掉"王后"的部分，剩下的方向和"男人"去掉"女人"一样，都是"性别"这个维度。这是词嵌入最迷人的地方。

**词嵌入（Word Embedding）的定义**：把一个 token 转换成多个维度的数字向量，这个过程就叫词嵌入。

> "嵌入（Embedding）"的本意：把**低维离散**的对象（一个个孤立的词），"镶嵌、植入"到一个**连续高维**的几何空间里。

## 6. 但谁来填这些值？

看完上面的例子你可能会问三个问题：

1. 每个 token 该有多少个维度？
2. 每个维度表达什么含义？
3. 每个维度的值是多少？

答案是——**人类只回答第一个问题（规定维度数），后两个问题交给机器在训练中自己找**。

> 核心思想：**在深度学习中，我们只规定学习方法，永远不要告诉机器答案。** 所以只规定"每个 token 用多少维"，让机器在训练过程中，自己为每个 token 的每个维度填上合适的值。填出来的维度含义往往人类也看不懂，但机器用起来很有效。

## 7. 两个相关术语

| 术语               | 含义                                                               |
| ------------------ | ------------------------------------------------------------------ |
| **上下文长度**     | 传入到 Transformer 神经网络的 **Token 数量**（一次实际传了多少个） |
| **上下文窗口长度** | Transformer 神经网络**能容纳的最大** Token 数量（上限）            |

> 大白话：上下文长度是"这次塞了几个 token"，上下文窗口长度是"最多能塞几个 token"。超窗口会截断或报错，这也是 [[【基础】Token统计]] 里"事前拦截超长文本"的底层原因。

## 8. 总结

- **为什么要嵌入**：Token ID 无法表示语义、无法做数学运算。
- **Token ID 的角色**：只是**索引/查表钥匙**——当行号去嵌入矩阵里取向量，自己不参与计算。
- **怎么做**：把 token 变成**多维向量**（查表取出），语义相近的词向量靠近。
- **向量语义关系**：国王−王后≈男人−女人，向量的加减开始有意义。
- **谁填值**：人类只规定维度数，机器在训练中自己填。
- **术语**：上下文长度（实际 token 数）、上下文窗口长度（最大 token 数）。
