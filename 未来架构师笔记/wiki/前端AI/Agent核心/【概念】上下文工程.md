> 2025 年 6 月，Shopify 的 CEO Tobi Lütke 在社交媒体上表示，他更喜欢用"上下文工程"这个词来替代"提示词工程"，因为它更准确地描述了**为 LLM 提供充分信息以完成任务**的核心技能。

[[【概念】提示词工程]] 关注"指令怎么写"，但模型真正读到的是一整段**上下文**：系统提示词、用户问题、历史对话、工具定义、检索到的资料……**上下文唯一地影响着模型的输出质量**。上下文工程（Context Engineering）研究的，就是如何把这段上下文组织好。

## 1. 上下文为什么难：注意力偏差

模型不是"均匀地"阅读上下文，它存在 **注意力偏差（Attention Bias）**，具体表现为四种现象：

### 1.1 长度稀释

上下文越长，注意力就被分散到更多 token 上，关键信息的权重被摊薄，模型更容易漏掉信息。

> 类比：一封 10 句话的邮件你能记住重点；一封 1000 句话的邮件，重点就淹没了。

### 1.2 长度分布外（OOD，Out-of-Distribution）

模型是在特定长度分布的语料上训练的。当上下文长度超过训练时常见的长度后，模型回复的置信度会明显下降——它"没见过这么长的场面"。

### 1.3 信噪比问题

噪声信息越多，越会挤占模型对关键信息的注意力预算。无关内容不只是"占地方"，而是**实实在在地削弱有效信息**。

### 1.4 首尾强化

模型对**开头**（系统提示词）和**结尾**（最近输入）的关注度天然高于**中间**（位置偏差 / Positional Bias）。所以关键信息应尽量放在首尾，而不是被埋在中间。

## 2. 上下文工程的两大关注点

### 2.1 编排（Orchestration）

**提示词、用户问题、工具、MCP、Skill 等内容在上下文中如何排列？什么时间加入什么内容？**

这正对应前几篇的机制设计：

- [[【基础】系统提示词]] 固定在最前面，作为全局约束；
- [[【实战】Skill 技能系统]] 只常驻清单，命中时才把正文追加进来，控制长度；
- 工具结果、MCP 返回按需写入，而不是一次性全塞。

编排的目标就是：**在正确的时刻，把正确的内容，放到正确的位置。**

### 2.2 治理（Governance）

治理回答两个问题：

- **如何确保上下文的内容安全可信？** 工具返回、外部网页、用户输入都可能包含不可信内容（提示词注入等），需要过滤与隔离。
- **如何在持续循环中管理不断膨胀的上下文？** Agent 每跑一轮都会追加工具结果，上下文只增不减。需要压缩、摘要、丢弃过期信息等策略。

## 3. 与提示词工程的关系

|          | 提示词工程           | 上下文工程                                   |
| -------- | -------------------- | -------------------------------------------- |
| 关注对象 | 指令文字             | 整个上下文                                   |
| 范围     | 局部                 | 全局                                         |
| 典型问题 | "这句话怎么写更清楚" | "什么内容该进上下文、什么时候进、怎么不膨胀" |

**提示词工程是上下文工程的一个子集。** 上下文越复杂，越需要从整体去设计和治理。

## 4. 总结

- **动因**：模型读的是完整上下文，而不只是提示词。
- **四条注意力偏差**：长度稀释、分布外、信噪比、首尾强化。
- **两大关注点**：编排（何时放入何内容、放哪里）与治理（安全可信 + 上下文膨胀管理）。
- **定位**：上下文工程是提示词工程的超集，是复杂 Agent 的必修课。

上下文管理清楚了，下一个问题更宏观：**怎样设计一整套"驾驭模型"的机制，让它在长周期任务里不跑偏、不越权、可判断成败？** 这就是 [[【概念】驾驭工程]]。
