### 1.2 这个页面只讲算术，不报价

下面的价格、分组倍率与用量均为教学假设，不代表任何厂商当前价格，也不是本机站点实际配置。规则来源见 [[【new-api】07-计费预扣结算与退款]]，目的只是看懂账是怎样算出来的。

本项目当前源码中的 `QuotaPerUnit` 默认值是 500000；实际理解某站点账单时还需看其配置与历史规则。这里把“1 美元对应 500000 个内部额度单位”作为算例约定。

---

### 1.3 token 数量如何变成美元

假设一次调用使用 1000 个输入 token、500 个输出 token。输入价每百万 token 2 美元，输出价每百万 token 6 美元。

$$
F = \frac{P \times R_p + C \times R_c}{1000000}
$$

| 符号 | 含义                        | 本例数值 |
| :--- | :-------------------------- | -------: |
| F    | 本次费用，单位美元          |   待计算 |
| P    | 输入 token 个数             |     1000 |
| C    | 输出 token 个数             |      500 |
| R_p  | 每百万输入 token 的美元价格 |        2 |
| R_c  | 每百万输出 token 的美元价格 |        6 |

为什么除以一百万？因为价格针对一百万个 token，1000 个只占这一批的一千分之一；先把“百万单价”除以一百万，才是一个 token 的价格。

逐步算：输入费是 1000 × 2 ÷ 1000000 = 0.002 美元；输出费是 500 × 6 ÷ 1000000 = 0.003 美元；合计 0.005 美元。

这是假设只有普通输入、普通输出两种互不重叠的资源。音频、缓存、固定请求费等不在这个简化公式里。

### 1.4 美元如何变成 quota

$$
Q = \operatorname{round}(F \times U \times G)
$$

| 符号  | 大白话                                 |
| :---- | :------------------------------------- |
| Q     | 本次要扣的整数额度                     |
| F     | 上一步算出的美元费用                   |
| U     | 每美元对应多少内部额度，本例取 500000  |
| G     | 本例假设的分组倍率，取 1               |
| round | 把结果变为整数；实际由项目额度工具执行 |

代入：0.005 × 500000 × 1 = 2500 quota。可以理解成先把美元换成平台记账单位，再应用本例倍率。

有些历史路径使用不同的截断 / 舍入语义；当前代码还有上限与非有限数保护。这里的算例结果本身是整数，不涉及争议边界，不能用它替代所有历史路径的实际计算规则。

### 1.5 预扣为什么不是额外消费

假设钱包原本 100000 quota，预计本次用 4000，实际只用 2500。

| 时点   | 操作                                  | 钱包剩余 |
| :----- | :------------------------------------ | -------: |
| 调用前 | 余额                                  |   100000 |
| 提交前 | 预留 4000                             |    96000 |
| 完成后 | 实际 2500，比预留少 1500，因此退 1500 |    97500 |

最终钱包减少 2500，正好等于实际消费。

$$
D = A - R
$$

这里 D 是结算差额，A 是实际费用额度，R 是已预扣额度。本例 D = 2500 − 4000 = −1500，负号表示退回 1500。如果实际为 5000，则差额为 1000，表示还要补扣 1000。

推导很直接：已经扣了 R，希望最终总共扣 A，所以还需扣 A − R。R 加上 A − R，正好等于 A。这解释了为什么不能先预扣、完成后再完整扣一次 A。

### 1.6 缓存 token 为什么会改变计价输入

假设某 OpenAI 风格上游返回输入总数 1000，其中缓存读取 200。没有其他模态或缓存交叠。

若表达式只有 `p * 2 + c * 6`，缓存未单独定价，本例全部 1000 输入按基础价。

若表达式为 `p * 2 + cr * 0.5 + c * 6`，`cr` 单独表示缓存读取数，则 `p` 为 800，`cr` 为 200。否则把 p 保持 1000 再加缓存费，就对这 200 个 token 重复算了一遍。

输出仍为 500 时：普通输入 800 × 2 = 1600；缓存 200 × 0.5 = 100；输出 500 × 6 = 3000。合计 4700，除以一百万得到 0.0047 美元，再按本例额度尺度得到 2350 quota。

这里表达式的 `p` 是“计价用输入余量”，`len` 是“完整输入上下文长度”。如果要按上下文长度选择价格档位，应看 `len`，否则缓存越多，错误地越容易落到低档位。

不同上游的计数口径可能不一样；例如 Claude 输入和缓存报告关系由归一化逻辑处理。上面只是一个已明确口径的算例。

### 1.7 图片和任务用量的直观算例

假设按张收费，每张 0.02 美元，生成两张，则 2 × 0.02 = 0.04 美元。普通图片表达式可以使用 `image_count` 配合固定价格语义；任务插件可以报告 `u("image_count")`。

**两种表达式的内部结果尺度不同。** 任务用量表达式直接得到美元；普通表达式由引擎按自己的约定转换。表达式字段不能直接互换，更不能先乘一次百万再套另一套换算。

至于应计一张还是两张，应回到实际有效载荷与插件规则，不是这个乘法本身决定。计价正确首先要求“数量”正确，见 [[【new-api】06-多模态与协议分支]] 与 [[【new-api】10-异步任务与JavaScript插件]]。
