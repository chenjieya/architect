### 1.4 模型广场：先选择，再比较

![[new-api-models-zh-CN-9b473a3.jpg]]

页面使用公开导航与居中的介绍区域，下面是搜索框；左侧按分组、厂商、标签、定价类型和端点筛选；右侧提供视图/单位/排序选择和模型卡片。每张卡片把模型标识、厂商、描述、能力、价格、可用分组与性能放在不同层级。

### 1.5 使用日志：高密度但可追溯

![[new-api-usage-logs-zh-CN-9b473a3.jpg]]

上方是时间、模型、分组、类型筛选和统计摘要，下方是表格。时间、渠道、用户、Key、模型、是否流式、输入/输出 token、费用、首字/总耗时和详情分别有列。主值和辅助值字号、颜色不同，模型和费用使用轻量徽标。

普通用户与管理员看到的字段应不同；详情里的计费规则帮助解释扣费，而不是暴露上游凭据。查询串、复制反馈、分页和导出范围都应有明确语义。移动端参考卡片化信息分组，不能简单挤压十列桌面表。

### 1.7 从源码提取的布局尺寸

| 项目     | 原始值/规则                          | 解释                                            |
| :------- | :----------------------------------- | :---------------------------------------------- |
| 顶栏高度 | `--app-header-height: 3rem`          | 根字号 16px 时约 48px；不是固定所有设备 48px    |
| 桌面侧栏 | `13rem`                              | 根字号 16px 时约 208px                          |
| 移动侧栏 | `17rem`                              | 抽屉展示，约 272px 的参考尺寸                   |
| 折叠侧栏 | `2.75rem`                            | 约 44px，保留图标导航                           |
| 移动判断 | 宽度小于 768px                       | 来自 use-mobile；其他容器查询仍可能有自己的阈值 |
| 默认布局 | `inset` + `icon` 折叠模式            | 内容区内嵌，侧栏可折为图标                      |
| 根圆角   | `--radius: 1rem`                     | sm/md/lg/xl 通过 0.6/0.8/1/1.4 倍等派生         |
| 内容高度 | 基于 `100svh` 减顶栏/内边距          | 独立内容滚动，避免整页多个无意滚动条            |
| 弹窗高度 | 动态视口 `100dvh` 与 safe-area inset | 移动端底部按钮不能被浏览器工具栏遮住            |

默认值可能被主题预设、用户设置或页面级样式覆盖。尺寸是源码证据，不是从截图估算。

### 1.8 颜色与排版

以下是 `theme.css` 中基础亮色主题的原始变量片段，不是完整 CSS 构建入口：

```css
:root {
  --radius: 1rem;
  --app-header-height: 3rem;
  --background: oklch(1 0 0);
  --foreground: oklch(0.145 0 0);
  --primary: oklch(0.692 0.141 243.716);
  --primary-foreground: oklch(1 0 0);
  --muted: oklch(0.97 0 0);
  --muted-foreground: oklch(0.49 0 0);
  --border: oklch(0.93 0 0);
  --destructive: oklch(0.577 0.245 27.325);
}
```

使用背景、文字、主操作、边框、弱化文字等语义变量，便于整套主题切换。暗色变量与预设已完整保存为离线源码。`index.css` 引入 Public Sans 与 Lora 等字体资源；自动字体模式的初始值是浏览器 sans-serif，不是所有用户始终使用 Public Sans。新项目前端还需自行解决字体加载，附件未打包字体二进制。

视觉风格是浅底色、细边框、圆角、少量蓝色主操作和较密的信息布局。不要把每张卡片都变成强阴影，也不要为了“现代感”改变字段含义和统计单位。

### 1.10 组件与交互规则

原前端使用 React、TanStack Router/Query/Table、Zustand、Base UI、Tailwind 等；后端换 Python 不会迫使前端换框架。这是架构解耦关系，不代表用户已选定 React。

组件参考分三层：基础 Button/Input/Dialog/Card/Table；通用复制、确认、表格、抽屉和表单保存操作；业务 Key 编辑、渠道配置、用量详情。原项目要求优先复用通用行为，不只是套一个 Button 就算完成复用。

ModelDock 页面验收建议：

- 查询具有 loading/error/empty 三种清楚状态，提交期间防止重复操作，失败后保留用户输入。
- 危险操作需要明确对象与后果；金额、单位、日期和语言使用统一格式化，不由每页自行拼字符串。
- 搜索与分页联动，改变筛选后回到合理页码；批量操作说明“当前页”还是“全部匹配项”。
- Key 复制与显示遵循后端安全契约，不将秘密写进地址栏或前端持久化日志。
- 键盘可进入弹窗、关闭后焦点返回，窄屏操作按钮可见，长表格与长 JSON 有明确滚动区域。
- 普通用户页面与管理员页面共享视觉组件，但权限和字段投影由后端保证。
