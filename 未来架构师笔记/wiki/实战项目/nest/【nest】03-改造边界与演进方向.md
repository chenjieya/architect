### 1.2 已确定与待确定事项

用户已确定：项目名为 **nest（汇聚之所）**，用于整合自己的所有项目；本次先整理架构文档。

以下为后续实施的讨论清单，尚不是完成项或已确认需求：

| 事项                               | 对实现的影响                         |
| :--------------------------------- | :----------------------------------- |
| 真实项目清单、地址、简介、公开范围 | 决定首批卡片内容，不能用模板站点代替 |
| 是否需要分类、搜索、置顶或详情     | 决定是否扩充数据模型与展示逻辑       |
| 天气、音乐、一言、壁纸的取舍       | 决定主页复杂度和外部服务依赖         |
| nest 的实际域名与部署路径          | 决定地址、资源 base、PWA 路径        |
| 内容维护方式                       | 继续静态文件，或另建管理能力         |
| 是否共享账号与跨项目数据           | 若需要，才进入认证与后端架构设计     |

当前架构见 [[【nest】01-现有架构与运行链路]]。本轮没有执行代码更名、依赖升级、目录移动或部署。

### 1.3 品牌更名涉及哪些位置

| 位置                                 | 当前行为                            | 后续修改点                                             |
| :----------------------------------- | :---------------------------------- | :----------------------------------------------------- |
| `package.json`                       | 包名 `home`                         | 包名可改为 `nest`；项目来源字段与当前产品信息分别处理  |
| `.env.example` 与实际 `.env`         | 模板名称、简介、域名、作者、备案等  | 标题与描述改为 nest 定位；真实地址与备案按实际资料配置 |
| `Message.vue`、`Main/Right.vue`      | 从域名分段生成大字标识              | 品牌文字从域名解析逻辑中独立出来                       |
| `App.vue`                            | 控制台硬编码原主页名称与图案        | 更新当前站点品牌输出                                   |
| `Footer.vue`                         | 环境变量作者信息 + package 来源信息 | 核对用户信息与项目来源展示                             |
| `public/images/icon/`、PWA manifest  | 模板图标与固定尺寸列表              | 统一应用图标和安装展示                                 |
| `siteLinks.json`、`socialLinks.json` | 原模板链接                          | 替换为真实项目与个人联系入口                           |
| `README.md`、`README_EN.md`          | 原模板说明                          | 后续整理 nest 使用与维护说明                           |
| `.github/workflows/build.yml`        | artifact 名称 `Home`                | 按实际发布流程更新名称                                 |

`LICENSE` 和原始来源标记属于单独核对的资料，不应在品牌文本替换时机械全局替换。源码文件夹目前叫 `home`，文件夹改名与产品名、包名是不同操作，还可能影响终端路径、CI 和编辑器配置。

字体也需核对：当前 `Pacifico-Regular.ttf` 使用压缩字库，仓库另有 `Pacifico-Regular-all.ttf`。新文字的实际字形覆盖情况应在浏览器检查，不能仅依据文件存在认定正确。

### 1.4 贴合当前目标的演进路径

下面是基于现有源码的建议，尚未实施，也没有新增依赖。

#### 1.4.1 先让项目入口成为主内容

优先复用现有静态构建、卡片组件和配置机制，明确每个项目的名称、用途和访问入口。先把模板数据替换为真实项目，再依据数量和查找需求判断是否需要分类或搜索。

保留个人风格的同时，使访客无需先打开附属面板便能看到项目。项目列表应能独立于天气、音乐、壁纸加载失败展示。

#### 1.4.2 按实际需求扩充项目数据

现有模型只有 `icon/name/link`。若增加分类与简介，可以在同一数据源中渐进扩展以下字段，而不立即引入后台系统：

| 字段建议              | 作用                         | 引入条件                   |
| :-------------------- | :--------------------------- | :------------------------- |
| `id`                  | 稳定标识，行为不绑定中文名称 | 实施项目列表改造时优先考虑 |
| `description`         | 让访问者理解项目用途         | 首页需要简介               |
| `category`            | 分组或筛选                   | 项目较多且有明确分类       |
| `tags`                | 辅助搜索与标记               | 明确搜索或标签需求         |
| `sort` / `featured`   | 排序或突出重点               | 用户需要固定展示顺序       |
| `repoUrl` / `docsUrl` | 源码与文档入口               | 确定展示这些信息           |

“已上线/开发中”等人工标记与“当前服务健康”不是同一信息。若要显示实时健康状态，需要定义数据来源、检测频率与失败含义；本仓库目前没有健康检测服务。

#### 1.4.3 只有需求出现时才增加架构层

单页静态目录可以继续承载项目聚合。独立项目详情页需要稳定 URL 时再考虑路由；多人在线编辑内容时再评估管理端和持久化；跨项目账号互通时再设计认证协议和权限边界。

产品名称 nest 不意味着必须使用 NestJS。当前源码没有 NestJS，也没有微前端子应用接入协议。

### 1.5 源码中已发现的具体问题

以下是静态代码发现和后续建议，不是浏览器复现报告，也不是完整安全或性能审计。

| 问题                          | 源码依据                                                                                     | 影响与处理建议                                                   |
| :---------------------------- | :------------------------------------------------------------------------------------------- | :--------------------------------------------------------------- |
| 项目列表受背景加载门控        | `App.vue` 的 `v-if="store.imgLoadStatus"`；`Background.vue` 只在图片成功后放行               | 本地回退图片也失败时可能一直不显示主内容；优先让核心入口独立就绪 |
| 品牌依赖域名拆分              | `Message.vue`、`Main/Right.vue` 的 `split('.')`                                              | 不适合直接展示 nest；分离品牌与地址                              |
| 音乐初始化未捕获 Promise 拒绝 | `Player.vue` 在 try 中调用 `.then()`，未 await 且未 `.catch()`                               | 接口异步失败不会进入该 catch；补正确错误边界                     |
| 歌单缺少空值保护              | `src/api/index.js` 直接读取 `data[0].url`                                                    | 空歌单或结构异常会抛错；先检查数组与字段                         |
| 外部歌词直接作为 HTML         | `Footer.vue` 的 `v-html="store.getPlayerLrc"`                                                | 未见显式净化步骤；纯文本歌词优先按文本渲染                       |
| UI 监听与全局赋值缺少完整清理 | `App.vue` 匿名 mousedown、`Music.vue` 匿名 keydown 和 `$openList`、`cursor.js` document 事件 | 组件反复挂载或未来路由化时易重复绑定；保存引用并统一卸载         |
| 请求缺少统一状态校验          | `src/api/index.js` 直接 `res.json()`                                                         | HTTP/业务失败缺少一致处理；按接口添加边界                        |
| 列表行为依赖名称              | `Links.vue` 判断 `name === '音乐'`                                                           | 项目更名可能改变行为；用稳定标识或明确动作字段                   |
| 设置音量 0 会被恢复为 0.7     | `Music.vue` 的 `store.musicVolume ? ... : 0.7`                                               | 刷新后静音偏好丢失；区分有效 0 与未设置                          |
| 天气无加载状态                | `Weather.vue` 数据未就绪直接进入失败文案                                                     | 请求期间可能显示误导提示；区分 loading/error/empty               |
| PWA API 未做能力判断          | `main.js` 直接使用 `navigator.serviceWorker`                                                 | 不支持该 API 的环境可能报错；先判断能力                          |
| Apple 图标路径不对应实际文件  | `.env.example` 指向 `/images/logo/apple-touch-icon.png`；文件在 `public/images/icon/`        | 修正配置并核对其他图标                                           |
| 安装链路未统一                | pnpm 锁文件与 Docker/CI 的 npm install                                                       | 不同环境解析依赖可能不同；固定工具与安装方式                     |

这些问题应结合后续功能范围安排，不在文档整理阶段顺手改代码。时间组件已有 `clearInterval`，背景组件已有 `clearTimeout`；不能把局部缺少清理扩大成“所有计时器都泄漏”。

### 1.6 建议的实施顺序与验收

| 阶段              | 主要产出                           | 可观察的验收结果                            |
| :---------------- | :--------------------------------- | :------------------------------------------ |
| 1：品牌与真实内容 | nest 标识、简介、真实项目卡片      | 标题、桌面/移动端名称一致；链接指向用户项目 |
| 2：核心可用性     | 解开壁纸门控、完善空数据与错误处理 | 外部服务失败时仍能查看和打开项目            |
| 3：列表体验       | 按已确认需求增加简介、分类或搜索   | 访客能理解用途并快速找到项目                |
| 4：发布一致性     | 统一构建、图标与缓存验证           | 本地与发布构建一致；旧缓存不阻碍品牌更新    |

实际编码前，将当批要修改的文件和功能边界列清楚。配置与现有发布链路见 [[【nest】02-配置构建与部署]]；专题入口见 [[【nest】00-项目定位与阅读地图]]。
