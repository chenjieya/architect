## 1. K8s 是什么

Kubernetes（简称 K8s，取首尾字母 + 中间 8 个字符）是开源的容器编排平台，用于管理**多台主机**上的容器化应用，提供应用部署、规划、更新、维护的机制。源于 Google 生产环境 15 年经验，2014 年开源。

**核心特性：**

| 特性               | 说明                                                              |
| ------------------ | ----------------------------------------------------------------- |
| 自动化装箱         | 基于容器资源需求和约束自动部署容器                                |
| 自愈能力           | 容器失败自动重启；Node 出问题自动重新调度；未通过健康检查自动关闭 |
| 水平扩容           | 按命令、界面或 CPU 使用率扩缩容                                   |
| 服务发现与负载均衡 | 无需额外机制即可发现服务、做负载均衡                              |
| 自动发布与回滚     | 程序化发布；发布有问题可回滚                                      |
| 保密和配置管理     | 不重建镜像即可更新配置和密钥                                      |
| 存储编排           | 自动挂接本地/云/NFS/Gluster/Ceph 等存储                           |

## 2. 集群架构

一个 K8s 集群由 **master 节点**和 **node 节点**组成。

- **master**：负责集群控制、Pod 调度、令牌管理等
- **node**：负责干活（启动容器、管理容器）
- master 和 node **不要部署在同一台机器**；生产高可用需部署多个 master

**每台机器都要装的软件包：**

| 软件      | 作用                            |
| --------- | ------------------------------- |
| `kubeadm` | 初始化集群的指令                |
| `kubelet` | 每个节点上启动 Pod 和容器的组件 |
| `kubectl` | 与集群通信的命令行工具          |

### 2.1 master 组件

| 组件                   | 职责                                                                 |
| ---------------------- | -------------------------------------------------------------------- |
| **API Server**         | 对外暴露 K8s API，是资源操作的**唯一入口**，提供认证、授权、访问控制 |
| **Scheduler**          | 负责资源调度，把新创建的 Pod 调度到合适的节点上                      |
| **Controller Manager** | 维护集群状态（故障检测、自动扩展、滚动更新等后台线程）               |
| **etcd**               | K8s 的后端数据库，K/V 方式存储**所有集群数据**，保存整个集群状态     |

## 3. Pod：K8s 最小工作单元

每个 Pod 包含一个或多个容器，是 K8s **调度、扩展、管理**的最小单位。

**为什么引入 Pod：**

1. **管理问题**：联系紧密的容器需要更高层次的抽象封装成部署单元
2. **共享资源**：Pod 内所有容器共用同一个**网络 namespace**（相同 IP 和端口空间），可直接用 localhost 通信；挂载 volume 本质是挂到 Pod 的每个容器上

**两种使用方式：**

- 一个 Pod 跑一个容器（最常见，Pod 可看作单容器的封装）
- 一个 Pod 跑多个容器（紧密协作，如"主容器 + sidecar 容器"共享文件）

## 4. Controller：Pod 的管理者

K8s 通常不直接创建 Pod，而是通过 **controller** 管理（几个副本、跑在哪个 Node 等）。

| Controller      | 用途                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------- |
| **Deployment**  | **最常用**，无状态应用部署；通过 ReplicaSet 管理 Pod 副本，支持滚动更新                           |
| **ReplicaSet**  | 实现 Pod 多副本管理；用 Deployment 时会自动创建，一般不需要直接使用                               |
| **DaemonSet**   | 每个 Node 最多运行**一个** Pod 副本（如日志收集 fluentd/logstash、监控 node-exporter、存储 ceph） |
| **StatefulSet** | 解决**有状态服务**：Pod 名称稳定不变、顺序启动/更新/删除（MySQL/MongoDB/ZooKeeper 集群）          |
| **Job**         | 批处理任务，跑完即结束                                                                            |
| **CronJob**     | 定时批处理任务                                                                                    |

> 记忆：Deployment/ReplicaSet 管**无状态**；StatefulSet 管**有状态**；DaemonSet 每个节点一个；Job 跑完就结束。

## 5. Service：访问入口

Pod 会被频繁销毁重建，IP 会变。**访问容器靠 Service**。

> 总结一句话：**K8s 运行容器通过 controller，访问容器通过 Service**。

Service 定义时需指定 `spec.type`，有四种：

| 类型                  | 说明                                                                    |
| --------------------- | ----------------------------------------------------------------------- |
| **ClusterIP**（默认） | 分配一个集群内虚拟 IP，**只能在集群内部访问**                           |
| **NodePort**          | 通过指定 Node 端口暴露给外部，访问 `NodeIP:nodePort` 会路由到 ClusterIP |
| **LoadBalancer**      | 在 NodePort 基础上借助云厂商创建外部负载均衡器，**仅云环境可用**        |
| **ExternalName**      | 通过 DNS CNAME 将服务转发到指定域名                                     |
