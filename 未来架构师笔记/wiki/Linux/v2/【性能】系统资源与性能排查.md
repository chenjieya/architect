## 1. 概述

线上最常见的一句话是“服务器好慢”。排查顺序永远是：**先判断慢在哪一类资源，再找是谁造成的，最后处理。** 这篇按 CPU、内存、磁盘、磁盘 IO、文件句柄、内核日志六条线展开。

## 2. 机器慢，慢在哪

![](https://picgo-1300696809.cos.ap-beijing.myqcloud.com/obsidian/1794631658293_51-resources.png)

_五类常见资源问题_

登录一台出问题的服务器，按这个顺序敲，几十秒内就能判断方向：

```bash
uptime                  # 负载高不高？
top                     # 谁在占 CPU 和内存？
free -h                 # 内存还剩多少？
df -h                   # 磁盘满了吗？
vmstat 1 5              # 在等 CPU、等磁盘，还是在换页？
sudo dmesg -T | tail    # 内核有没有报错（比如进程被杀）？
```

## 3. CPU

### 3.1 uptime 与平均负载

```text
$ uptime
 14:07:18 up 3 days,  2:10,  1 user,  load average: 0.52, 0.30, 0.10
```

`load average` 后面三个数字，依次是最近 **1、5、15 分钟**的平均负载，可以理解为“平均有多少个任务在排队等 CPU”。

比如 1 分钟的值是 0.5，可以粗略理解为：前半分钟有 1 个进程在运行，后半分钟空闲。

```bash
nproc          # 查 CPU 核数
```

和核数比：4 核的机器，负载长期在 4 左右就是满了。**1 分钟的值比 15 分钟大，说明正在变忙。**

### 3.2 top

进入 `top` 后：

```text
P : 按 CPU 排序（默认）
M : 按内存排序
1 : 展开每个 CPU 核
q : 退出
```

![](https://picgo-1300696809.cos.ap-beijing.myqcloud.com/obsidian/1794631658296_52-top.png)

_`top` 输出重点：负载、CPU 行、进程列表_

`%Cpu` 那一行：`us` 是用户程序占用，`wa` 是在等磁盘，`id` 是空闲。进程列表里的 `%CPU` 在多核机器上可以超过 100%。

用一个占满 CPU 的命令试一试：

```bash
yes > /dev/null &        # 不停输出 y，输出丢进 /dev/null（黑洞），& 后台运行
top                      # 可以看到 yes 的 %CPU 接近 100%，按 q 退出
kill %1                  # 结束它
```

不进 `top` 也可以直接用 `ps` 排序：

```bash
ps aux --sort=-%cpu | head -5
```

## 4. 内存

```text
$ free -h
               total        used        free      shared  buff/cache   available
Mem:           7.8Gi       504Mi       7.3Gi        14Mi       301Mi       7.3Gi
Swap:             0B          0B          0B
```

![](https://picgo-1300696809.cos.ap-beijing.myqcloud.com/obsidian/1794631658297_53-free.png)

_`free -h` 各列含义_

内存不够用时，系统会把一部分内存内容写到磁盘上，这就是 **swap**（交换空间）。磁盘比内存慢得多，swap 被大量使用，机器就会明显变慢。

看内存被谁占了：

```bash
ps aux --sort=-%mem | head -5      # 按内存排序，前 5 个
```

在 `top` 里按 `M` 效果一样。

## 5. 磁盘空间

```text
-h : human-readable  用 G、M 这样的单位显示
-s : summarize       只显示总数
```

### 5.1 df：分区还剩多少

```text
$ df -h
Filesystem           Size  Used Avail Use% Mounted on
/dev/mapper/rl-root   36G  2.9G   33G   9% /
tmpfs                3.9G     0  3.9G   0% /dev/shm
```

`Use%` 是使用率，超过 85% 就该关注。`df -i` 看 inode 使用情况：**文件数量太多时，即使空间没满也会写不进去。**

### 5.2 du：谁占的空间

`df` 告诉你“满了”，`du` 告诉你“谁占的”：

```bash
sudo du -sh /var/tmp                          # 这个目录一共多大
sudo du -h --max-depth=1 /var | sort -h       # 只看下一层，按大小排序，最后几行是大户
sudo find /var -type f -size +500M            # 直接找大文件
```

造一个 1G 的文件，模拟磁盘被占：

```bash
# if  : input file，/dev/zero 会不断吐出二进制的 0
# of  : output file，目标文件
# bs  : block size，每块 1M
# count: 搬运 1024 次，合计 1G
$ dd if=/dev/zero of=/var/tmp/big.bin bs=1M count=1024
1024+0 records in
1024+0 records out
1073741824 bytes (1.1 GB, 1.0 GiB) copied, 1.2 s, 893 MB/s

$ du -sh /var/tmp
1.0G	/var/tmp

$ find /var -type f -size +500M
/var/tmp/big.bin

$ rm /var/tmp/big.bin
```

## 6. 磁盘 IO

机器很慢、CPU 却不高，常常是**在等磁盘**。

### 6.1 vmstat

```text
r  : 等着用 CPU 的进程数，长期大于 CPU 核数，说明 CPU 不够
b  : 被阻塞（通常在等 IO）的进程数，持续大于 0，说明在等磁盘
si : 从 swap 换入        so : 往 swap 换出，持续不为 0，说明内存不够
bo : 往磁盘写的数据量
wa : 等待 IO 的 CPU 时间百分比，高，说明磁盘是瓶颈
```

`vmstat 1 5` 每秒输出一行，共 5 次。一个磁盘忙碌时的输出：

```text
$ vmstat 1 5
procs -----------memory----------    ---swap--  -----io---- -system-- -------cpu-------
 r  b   swpd   free   buff  cache      si   so    bi    bo   in  cs  us sy id wa st
 1  1      0 6763921 105948 1048780    0    0     0 516136 4226 5613  0 15 44 39  1
 0  1      0 6782344 105948 1029900    0    0     0 506856 3445 5071  0 13 47 40  1
```

`id` 还有 44%，但 `wa` 高达 39%，`b` 是 1：**CPU 闲着，是在等磁盘。** 第一行是开机以来的平均值，从第二行开始看。

用一个不停写磁盘的命令试一试：

```bash
dd if=/dev/urandom of=/var/tmp/io.bin bs=1M count=3000 oflag=direct &   # 后台持续写磁盘
vmstat 1                                                               # 看 bo 和 wa
rm /var/tmp/io.bin                                                     # 写完后删除
```

### 6.2 iostat

进一步观察哪个**块设备**繁忙（默认按设备统计，不等同于每个分区的实际业务贡献）。

`iostat` 属于 `sysstat` 软件包：

```bash
sudo dnf install -y sysstat

iostat -x 1 3        # 每秒采集一次，共 3 次；-x 显示扩展信息
lsblk                # 查看磁盘与分区的逻辑关系
```

```text
%util   : 磁盘忙碌的时间占比，接近 100% 说明磁盘已经饱和
await   : 一次 IO 平均等待多少毫秒，持续很高说明磁盘响应慢
r/s w/s : 每秒读 / 写次数
```

## 7. 文件句柄与 lsof

### 7.1 什么是文件描述符

程序运行时需要访问各种资源：读配置文件、写日志、监听端口、建立 TCP 连接。Linux 用**文件描述符（File Descriptor，FD）**让进程访问这些已打开的资源。

FD 通常是一个非负整数，例如 `0、1、2、3、4`：

| FD       | 通常对应                 |
| -------- | ------------------------ |
| 0        | 标准输入 stdin           |
| 1        | 标准输出 stdout          |
| 2        | 标准错误 stderr          |
| 3 及以上 | 普通文件、Socket、管道等 |

一台 Web 服务器接受多个客户端连接，这些连接都要占用 FD。**打开的文件和连接越多，占用的 FD 就越多。** 每个进程能打开的 FD 有上限，达到上限就会出现：

```text
Too many open files
```

### 7.2 lsof：查看打开的文件

`lsof` 是 List Open Files 的缩写，能看普通文件、网络 Socket 等。最小安装可能没有，先装：

```bash
sudo dnf install -y lsof
```

**实验一：谁在使用 SSH 的 22 端口**

```bash
sudo lsof -nP -iTCP:22 -sTCP:LISTEN
```

- `-iTCP:22`：查看与 TCP 22 端口有关的网络资源；
- `-sTCP:LISTEN`：只筛选监听状态；
- `-nP`：不做主机名和端口名解析。

```text
COMMAND PID USER FD  TYPE NAME
sshd    921 root 3u  IPv4 TCP *:22 (LISTEN)
```

| 列      | 含义                               |
| ------- | ---------------------------------- |
| COMMAND | 进程名称                           |
| PID     | 进程编号                           |
| USER    | 进程所属用户                       |
| FD      | 文件描述符（`3u` 表示 3 号、读写） |
| TYPE    | 资源类型                           |
| NAME    | 资源的具体信息                     |

**实验二：指定进程打开了哪些资源**

```bash
sudo lsof -p 921
```

![](https://picgo-1300696809.cos.ap-beijing.myqcloud.com/obsidian/1794631658299_image-20261102110557879.png)

_`lsof -p` 查看单个进程打开的资源_

> 921 是示例 PID，实际要换成你查到的进程号。`lsof` 输出里除数字 FD 外还有 `cwd`、`txt`、`mem` 等条目，**不能直接把总行数当 FD 数量**。

### 7.3 查看 FD 数量与限制

统计进程当前打开的 FD 数量：

```bash
sudo ls -1 /proc/921/fd | wc -l
```

假设输出 `25`，表示该进程当前大约打开了 25 个 FD（`/proc/921/fd` 是该进程的 FD 目录，`wc -l` 统计行数）。

查看当前 Shell 的软限制：

```bash
ulimit -n
```

假设输出 `1024`。注意它查看的是**当前 Shell**，不是任意进程。要看 PID 921 的限制：

```bash
cat /proc/921/limits
```

在输出里找 `Max open files`，其中包含软限制（Soft Limit）和硬限制（Hard Limit）。

### 7.4 运维场景：Too many open files

某个 JavaWeb 服务运行一段时间后报：

```text
java.io.IOException: Too many open files
```

按顺序排查：

```bash
pgrep -af java                          # 1 定位 Java 进程，记下 PID
sudo ls -1 /proc/PID/fd | wc -l         # 2 当前打开了多少 FD
cat /proc/PID/limits                    # 3 进程的 FD 限制
sudo lsof -p PID                        # 4 具体打开了哪些资源
```

重点看是否打开了大量日志文件，或存在大量网络连接。如果 FD 数量持续异常增长并接近上限，可能存在文件或 Socket 没正确关闭，也就是**文件描述符泄漏（FD Leak）**。

注意：FD 增长不一定是泄漏，高并发服务也可能正常维护大量连接。**提高上限只能缓解，根本原因在程序没关资源时仍需改程序。** 遇到 `Too many open files`，先确认“哪个进程、打开多少、限制多少、是否异常增长”，不要上来就调大限制。

## 8. 内核日志与 dmesg

### 8.1 内核日志是什么

Linux 运行过程中，不仅应用会产生日志，**内核本身也会记录重要系统事件**，例如：

- 启动时识别到哪些硬件设备；
- 磁盘读写是否出现错误；
- 内存不足时是否触发 OOM（Out Of Memory）；
- 某些驱动是否异常；
- 是否发生硬件或内核相关错误。

例如某个 Java 服务突然消失，应用日志没有明显错误，但内核日志里有：

```text
Out of memory: Killed process 1234 (java)
```

这说明系统曾发生内存不足，内核终止了该 Java 进程。

`dmesg`（Display Message）读取内核消息缓冲区，**主要看内核消息，不是应用日志**。

### 8.2 查看与筛选

```bash
sudo dmesg                 # 输出内核消息缓冲区
sudo dmesg | tail -20      # 只看最后 20 行
```

默认时间是从系统启动开始计算的秒数：

```text
[    0.000000] Linux version 5.14.0...
[    1.235678] nvme nvme0: pci function 0000:03:00.0
[   12.567890] EXT4-fs (sda1): mounted filesystem
```

不方便和故障时刻对应，加 `-T` 转成可读日期：

```bash
sudo dmesg -T | tail -20
```

```text
[Mon Nov  2 10:15:32 2026] nvme nvme0: I/O error
```

> `-T` 的转换可能受系统时间调整、休眠等影响，不一定完全精确，实际要结合其他日志确认时间。

筛选错误：

```bash
sudo dmesg -T | grep -i error
sudo dmesg -T | grep -iE "error|fail|oom"     # -E 扩展正则，| 表示“或”
```

这类筛选只能快速找可疑消息，不能保证所有故障都含这些关键字。

### 8.3 常见内核日志

**内存不足（OOM）：**

```text
Out of memory: Killed process 1234 (java)
```

- `Out of memory`：内存不足；
- `Killed process`：进程被内核终止；
- `1234`：被终止进程的 PID；
- `(java)`：进程名。

这与 **OOM Killer** 机制有关：系统无法满足内存分配时，内核可能终止一个或多个进程来缓解压力。查 OOM 记录：

```bash
sudo dmesg -T | grep -iE "out of memory|oom|killed process"
```

不是所有程序异常退出都由 OOM 引起，还要结合时间、进程名和内存使用判断。

**磁盘 I/O 错误：**

```text
I/O error, dev sda, sector 123456
```

- `I/O error`：输入输出错误；
- `dev sda`：涉及的块设备；
- `sector 123456`：涉及的扇区。

可能与磁盘、虚拟存储设备、驱动或底层存储环境有关。查相关记录：

```bash
sudo dmesg -T | grep -iE "I/O error|blk_update_request|nvme"
```

大量 I/O 错误要进一步检查块设备与存储系统，**不能简单认定是物理硬盘损坏**。

**驱动或设备初始化异常：**

```text
device initialization failed
```

```bash
sudo dmesg -T | grep -iE "failed|timeout|reset"
```

服务器识别不到磁盘、网卡等硬件时，这类信息有参考价值。以上日志均为示例，不同发行版输出可能不同。

### 8.4 实战：Java 服务突然消失

**第一步：确认进程是否存在**

```bash
pgrep -af java
```

找不到进程，只说明它可能已退出；还可能是程序崩溃、人工停止、服务管理器终止，不能直接断定是内存问题。

**第二步：看内核日志**

```bash
sudo dmesg -T | tail -50
sudo dmesg -T | grep -iE "oom|out of memory|killed process"
```

看到 `Out of memory: Killed process 1234 (java)`，说明发生过 OOM，且内核终止了 PID 1234 的 Java 进程。还要结合日志时间，确认是否与本次故障对应。

**第三步：看当前内存**

```bash
free -h
vmstat 1 5
```

重点看 `free -h` 的 `available` 和 `Swap`，以及 `vmstat` 的 `si`（swap 换入）、`so`（swap 换出）。

注意：**OOM 发生后进程已经被杀，当前内存可能已恢复正常**，不能只凭故障后的 `free -h` 判断当时是否内存不足。

**第四步：分析原因**

如果确认是 OOM，继续查：

- Java 服务是否占用过多内存；
- 虚拟机分配的物理内存是否不足；
- 是否还有其他进程大量消耗内存；
- 是否存在内存泄漏或程序配置不合理；
- 是否受到容器或 systemd 服务的内存限制。

Java 服务还要结合 JVM 堆配置和应用日志。**不能只靠加 Swap 或重启程序就认为问题解决了。**

### 8.5 用 journalctl 看内核日志

systemd 系统（如 Rocky Linux 9）还可以：

```bash
sudo journalctl -k -b        # -k 只看内核消息，-b 本次启动
sudo journalctl -k -b -1     # 上一次启动的内核日志
```

这在服务器重启后排查之前的内核错误很有用，前提是 journal 日志已持久化保存；未保存则查不到。

## 9. 命令速查

```bash
# 快速巡检
uptime                          top
free -h                         df -h
vmstat 1 5                      sudo dmesg -T | tail
# CPU
nproc                           ps aux --sort=-%cpu | head -5
# 内存
ps aux --sort=-%mem | head -5
# 磁盘
df -h / df -i                   du -sh 目录
du -h --max-depth=1 目录 | sort -h
find 目录 -type f -size +500M
# 磁盘 IO
iostat -x 1 3                   lsblk
# 文件句柄
sudo lsof -nP -iTCP:端口 -sTCP:LISTEN
sudo lsof -p PID
sudo ls -1 /proc/PID/fd | wc -l
ulimit -n                       cat /proc/PID/limits
# 内核日志
sudo dmesg -T | tail -50
sudo dmesg -T | grep -iE "error|fail|oom"
sudo journalctl -k -b / -b -1
```
