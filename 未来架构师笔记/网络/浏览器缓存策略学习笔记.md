## 1. 浏览器缓存策略学习笔记：强缓存、协商缓存与常见组合

---

### 1.1 概述

浏览器缓存不要理解成“强缓存配置”和“协商缓存配置”两套互斥开关。更准确的理解是：浏览器拿到一个响应后，会保存响应体和一组缓存元信息；下次请求同一个缓存键时，按这些元信息决定是否直接用、是否要找服务器验证。

常用术语：

- 强缓存：浏览器在本地判断缓存仍有效，直接使用本地副本，不向服务器发请求。
- 协商缓存：浏览器向服务器发条件请求，服务器判断资源是否变化；未变化返回 `304 Not Modified`，变化返回 `200 OK` 和新内容。
- 新鲜度：缓存是否还在可直接使用的有效期内，由 `Cache-Control: max-age`、`Expires` 或浏览器启发式规则决定。
- 验证器：用于问服务器“我这个本地版本还能不能用”的字段，主要是 `ETag` 和 `Last-Modified`。

核心记忆：

> 缓存流程先看“本地缓存是否新鲜”；不新鲜或被要求验证时，再看“有没有验证器可以发起协商缓存”。

---

### 1.2 浏览器缓存决策顺序

#### 1.2.1 基本流程

```text
请求某个 URL
  ↓
本地是否有可用缓存？
  ↓
没有：发请求，通常拿到 200 和响应体
  ↓
有：检查 Cache-Control / Expires / 启发式规则判断是否新鲜
  ↓
新鲜：直接使用本地缓存，不发请求（强缓存命中）
  ↓
不新鲜，或 Cache-Control 要求验证：准备向服务器验证
  ↓
有 ETag：带 If-None-Match 发请求
没有 ETag 但有 Last-Modified：带 If-Modified-Since 发请求
两个都没有：只能普通请求，通常返回 200
  ↓
服务器判断资源版本
  ↓
未变化：304，浏览器继续使用本地缓存体，并更新缓存元信息
已变化：200，服务器返回新文件，浏览器更新本地缓存
```

#### 1.2.2 常见状态对照

| 场景               | 是否发请求 | 服务端状态码 | 浏览器使用内容     |
| :----------------- | :--------: | :----------: | :----------------- |
| 强缓存命中         |     否     | 无网络状态码 | 本地缓存内容       |
| 协商缓存命中       |     是     |    `304`     | 本地缓存内容       |
| 缓存过期且资源已变 |     是     |    `200`     | 服务端返回的新内容 |
| 首次请求           |     是     |    `200`     | 服务端返回的新内容 |
| `no-store`         |     是     |  通常 `200`  | 不保存缓存副本     |

---

### 1.3 字段来源与组合关系

#### 1.3.1 Cache-Control、ETag、Last-Modified 不是一类东西

| 字段                | 谁返回       | 属于哪类信息 | 作用                                               |
| :------------------ | :----------- | :----------- | :------------------------------------------------- |
| `Cache-Control`     | 服务端响应头 | 缓存策略     | 告诉浏览器能不能存、能直接用多久、是否必须验证     |
| `Expires`           | 服务端响应头 | 缓存策略     | 用绝对时间表达过期时间，优先级低于 `Cache-Control` |
| `ETag`              | 服务端响应头 | 验证器       | 给资源一个版本标识，后续用于协商缓存               |
| `Last-Modified`     | 服务端响应头 | 验证器       | 给资源一个最后修改时间，后续用于协商缓存           |
| `If-None-Match`     | 浏览器请求头 | 条件请求     | 浏览器把上次的 `ETag` 带回服务器验证               |
| `If-Modified-Since` | 浏览器请求头 | 条件请求     | 浏览器把上次的 `Last-Modified` 带回服务器验证      |

关键点：

- 配置 `Cache-Control` 不会自动生成 `ETag`。
- 配置 `ETag` 也不等于配置了强缓存有效期。
- `ETag` / `Last-Modified` 通常由 Web 服务器、对象存储、CDN、后端框架或静态资源服务自动生成，也可以由应用层主动设置。
- 浏览器收到 `ETag` 后，下次需要验证时才会自动带上 `If-None-Match`。
- 浏览器收到 `Last-Modified` 后，下次需要验证时才会自动带上 `If-Modified-Since`。

#### 1.3.2 Cache-Control 可以配置多个指令

`Cache-Control` 是一个响应头，里面可以组合多个指令：

```http
Cache-Control: public, max-age=31536000, immutable
```

也可以写成多行响应头，由 HTTP 语义合并理解：

```http
Cache-Control: public
Cache-Control: max-age=31536000
Cache-Control: immutable
```

实际项目更推荐写成一行，便于排查。

`Cache-Control` 的多个指令不是按书写顺序决定优先级，而是按指令语义共同生效。它也不是按“强缓存配置优先”或“协商缓存配置优先”来排序，而是进入缓存流程后分别影响不同阶段：

```text
能不能存？
  看 no-store / private / public 等

能不能直接用？
  看 max-age / s-maxage / Expires / no-cache 等

过期后能不能继续用旧响应？
  看 must-revalidate / proxy-revalidate 等

需要验证时怎么验证？
  看 ETag / Last-Modified
```

常见规则：

| 组合                                  | 生效理解                                                              |
| :------------------------------------ | :-------------------------------------------------------------------- |
| `public, max-age=31536000, immutable` | 可以被缓存，强缓存一年，有效期内认为内容不可变                        |
| `no-cache, max-age=3600`              | 语义冲突；`no-cache` 要求每次使用前验证，不应期望 3600 秒内直接强缓存 |
| `no-store, max-age=3600`              | 语义冲突；`no-store` 更严格，要求不保存响应                           |
| `s-maxage=600, max-age=3600`          | 共享缓存按 `s-maxage`，浏览器私有缓存按 `max-age`                     |
| `max-age=3600` + `Expires`            | `max-age` 优先，`Expires` 作为旧兼容                                  |
| `max-age=60, max-age=120`             | 重复同名指令，语义不可靠；不要这样配置                                |

项目约定：不要写冲突或重复指令。需要“每次验证”就写 `no-cache`；需要“长期强缓存”就写 `public, max-age=31536000, immutable`；需要“不保存”就写 `no-store`。

#### 1.3.3 常见组合怎么理解

| 响应头组合                                     | 浏览器行为                                                  |
| :--------------------------------------------- | :---------------------------------------------------------- |
| `Cache-Control: max-age=3600` + `ETag`         | 1 小时内强缓存；1 小时后可用 `ETag` 协商，未变返回 304      |
| `Cache-Control: no-cache` + `ETag`             | 可以存本地，但每次使用前都要带 `If-None-Match` 验证         |
| `Cache-Control: no-cache` + `Last-Modified`    | 可以存本地，但每次使用前都要带 `If-Modified-Since` 验证     |
| `Cache-Control: no-store` + `ETag`             | 语义冲突；`no-store` 要求不保存，后续通常没有本地副本可验证 |
| 只有 `ETag`，没有显式新鲜度                    | 可能被浏览器启发式缓存；过期后可协商                        |
| 只有 `Cache-Control: max-age=3600`，没有验证器 | 1 小时内强缓存；过期后通常只能重新拿 200                    |

### 1.4 强缓存与新鲜度

#### 1.4.1 Cache-Control

`Cache-Control` 是 HTTP/1.1 的主要缓存控制头，优先级高于 `Expires`。

| 指令               | 含义                                         | 常见用法                            |
| :----------------- | :------------------------------------------- | :---------------------------------- |
| `max-age=31536000` | 从响应生成开始，缓存有效秒数                 | 带 hash 的静态资源                  |
| `no-cache`         | 可以缓存，但每次使用前必须向服务端再验证     | `index.html` 常用；它不是“不存缓存” |
| `no-store`         | 不缓存请求或响应内容                         | 登录、隐私、敏感接口                |
| `public`           | 可以被浏览器和共享缓存缓存                   | 公共静态资源                        |
| `private`          | 只能被单个用户浏览器缓存                     | 用户私有响应                        |
| `immutable`        | 有效期内认为内容不会变化，减少刷新时的再验证 | 带 hash 静态资源                    |
| `must-revalidate`  | 过期后必须向服务端验证，不能直接使用过期缓存 | 需要严格一致性的资源                |
| `s-maxage=600`     | 共享缓存有效期，优先于 `max-age`             | CDN / 代理缓存                      |

#### 1.4.2 `no-cache` 到底算强缓存还是协商缓存

`Cache-Control: no-cache` 容易被名字误导。它不是“不缓存”，而是：

> 可以存缓存，但不能直接拿来用；每次复用前必须先找服务器验证。

所以它的位置比较特殊：

- 它是 `Cache-Control` 里的缓存策略指令。
- 它会禁用“直接使用本地副本”的强缓存命中。
- 如果响应里有 `ETag` 或 `Last-Modified`，下次请求会进入协商缓存。
- 如果没有任何验证器，下次也要请求服务器，但很可能只能拿到 `200`。

示例：

```http
Cache-Control: no-cache
ETag: "app.abc123"
```

后续请求：

```http
If-None-Match: "app.abc123"
```

服务器判断未变化：

```http
304 Not Modified
```

服务器判断已变化：

```http
200 OK
ETag: "app.def456"
```

#### 1.4.3 Expires

`Expires` 是 HTTP/1.0 的过期时间头，值是一个绝对时间。

```http
Expires: Thu, 30 Jul 2026 10:00:00 GMT
```

缺点：

- 依赖客户端和服务端时间是否一致。
- 表达能力弱，不如 `Cache-Control` 明确。

如果同时存在：

```http
Cache-Control: max-age=3600
Expires: Thu, 30 Jul 2026 10:00:00 GMT
```

浏览器优先按 `Cache-Control` 判断。

#### 1.4.4 都不配置时浏览器有没有默认缓存

有可能有，但不能依赖。

如果响应没有显式新鲜度配置：

```http
Cache-Control
Expires
```

浏览器和中间缓存仍可能根据 HTTP 规范做“启发式缓存”。常见判断依据包括：

- 响应方法通常是 `GET` 或 `HEAD`。
- 状态码是可缓存状态，例如 `200`、`203`、`204`、`206`、`301`、`404`、`410` 等。
- 响应里有 `Date`、`Last-Modified` 等可推算资源年龄的信息。
- 响应没有 `Authorization` 等会限制共享缓存的条件。

##### 1.4.4.1 启发式缓存是什么

启发式缓存是浏览器在服务端没有明确告诉“缓存多久”时，自己估算一个新鲜期。

典型响应：

```http
HTTP/1.1 200 OK
Date: Thu, 30 Jul 2026 10:00:00 GMT
Last-Modified: Thu, 30 Jul 2026 09:00:00 GMT
ETag: "abc123"
```

没有：

```http
Cache-Control: max-age=...
Expires: ...
```

浏览器可能会推断：

```text
资源已经 1 小时没改了
那它短时间内也可能不会变
可以给它一个较短的新鲜期
```

常见启发式策略是：根据 `Date - Last-Modified` 推一个较短的新鲜期，例如取其中一部分时间。不同浏览器、代理、CDN 可能有差异，不要把这个比例当成稳定业务规则。

##### 1.4.4.2 启发式缓存和验证器的关系

有验证器不代表每次都会立刻协商。

如果没有显式 `Cache-Control` / `Expires`，但有 `ETag` 或 `Last-Modified`，可能出现两阶段：

```text
启发式新鲜期内：
  浏览器直接用本地缓存，不发请求

启发式新鲜期过后：
  浏览器用 ETag / Last-Modified 发起协商缓存
  未变化：304
  已变化：200
```

也就是说：

```http
ETag: "abc123"
```

只提供了“怎么验证”的能力；它不等于“每次都验证”。

如果希望每次都验证，应显式配置：

```http
Cache-Control: no-cache
ETag: "abc123"
```

更精确地记：

- `Last-Modified` 有两个作用：既可以作为启发式新鲜期估算依据，也可以作为协商缓存验证器。
- `ETag` 主要是协商缓存验证器，通常不用于估算启发式新鲜期。
- `If-None-Match` / `If-Modified-Since` 是浏览器下次请求时带的条件请求头，不是服务端第一次响应时返回的头。
- Nginx 的 `if_modified_since` 是服务端如何处理 `If-Modified-Since` 的配置项，不是浏览器缓存策略响应头。

因此，在没有 `Cache-Control` / `Expires` 时，常见流程是：

```text
浏览器已有本地缓存
  ↓
先判断缓存是否新鲜
  ↓
没有明确新鲜期时，可能用 Last-Modified 做启发式估算
  ↓
启发式判断仍新鲜：直接用本地缓存，不发请求
  ↓
启发式判断已过期，或刷新触发验证：带 If-None-Match / If-Modified-Since 请求服务器
  ↓
服务器返回 304 或 200
```

如果只有 `ETag`，没有 `Last-Modified` 和显式新鲜期，浏览器缺少常见的启发式估算依据，实际表现可能更倾向重新验证；具体仍以浏览器实现和刷新方式为准。

##### 1.4.4.3 只有 Date 的裸响应为什么通常不启发式缓存

类似三维地形瓦片经过甲方 Nginx 反代后的响应：

```http
HTTP/1.1 200 OK
Date: Fri, 31 Jul 2026 01:22:37 GMT
Server: nginx/1.30.1
Transfer-Encoding: chunked
```

如果响应里没有：

```http
Cache-Control
Expires
ETag
Last-Modified
```

浏览器通常没有明确新鲜期，也没有可靠的启发式估算依据。`Date` 只能说明本次响应生成时间，不能说明资源已经稳定了多久；没有 `Last-Modified` 时，常见的 `Date - Last-Modified` 估算无法成立。

这种情况下，即使浏览器临时保存了响应，也可能很快认为缓存不可直接复用；同时又没有 `ETag` / `Last-Modified`，下次也无法带条件请求头发起协商缓存，结果常见为：

```text
再次请求同一瓦片 URL
  ↓
没有可用强缓存
  ↓
没有 If-None-Match / If-Modified-Since
  ↓
服务端返回 200 OK，重新传输响应体
```

`Transfer-Encoding: chunked` 本身不等于禁止缓存；真正的问题是响应缺少明确缓存策略和验证器。

##### 1.4.4.4 启发式缓存的风险

启发式缓存的问题是不稳定：

| 风险           | 说明                                                     |
| :------------- | :------------------------------------------------------- |
| 浏览器差异     | 不同浏览器可能估算不同新鲜期                             |
| CDN / 代理差异 | 中间缓存可能有自己的启发式策略                           |
| 发布时间不可控 | 未显式配置时，用户可能短时间拿到旧资源                   |
| 排查困难       | Network 面板看到缓存命中，但响应头里没有明确的 `max-age` |

所以“什么都不配”并不等于“一定不缓存”。它更准确是：

> 没有明确缓存策略，浏览器可能按自己的启发式规则缓存，也可能重新验证或重新请求；线上不要依赖这种默认行为。

推荐项目里明确配置：

- `index.html`：`Cache-Control: no-cache`
- 带 hash 静态资源：`Cache-Control: public, max-age=31536000, immutable`
- 敏感接口：`Cache-Control: no-store`

### 1.5 协商缓存与验证器

#### 1.5.1 ETag / If-None-Match

`ETag` 是服务端给资源生成的版本标识。

第一次响应：

```http
ETag: "app.abc123"
```

后续请求：

```http
If-None-Match: "app.abc123"
```

服务端判断：

- 资源未变化：返回 `304 Not Modified`，不返回响应体。
- 资源已变化：返回 `200 OK`，返回新响应体和新的 `ETag`。

注意：上面只展示验证器本身。实际是否“立刻验证”，还要看 `Cache-Control` 或缓存是否过期。

例如：

```http
Cache-Control: max-age=3600
ETag: "app.abc123"
```

含义是：

- 1 小时内：强缓存命中，不发请求。
- 1 小时后：缓存变 stale，浏览器可带 `If-None-Match` 去协商。

#### 1.5.2 Last-Modified / If-Modified-Since

`Last-Modified` 是资源最后修改时间。

第一次响应：

```http
Last-Modified: Thu, 30 Jul 2026 08:00:00 GMT
```

后续请求：

```http
If-Modified-Since: Thu, 30 Jul 2026 08:00:00 GMT
```

服务端判断：

- 资源最后修改时间没有更新：返回 `304`。
- 资源最后修改时间更新：返回 `200` 和新内容。

#### 1.5.3 ETag 与 Last-Modified 的区别

| 对比项                       | ETag                 | Last-Modified  |
| :--------------------------- | :------------------- | :------------- |
| 判断依据                     | 内容版本标识         | 文件修改时间   |
| 精度                         | 可精确到内容 hash    | 通常秒级       |
| 是否能识别“时间变但内容没变” | 可以，取决于生成策略 | 不一定         |
| 是否能识别“一秒内多次变化”   | 可以，取决于生成策略 | 可能不行       |
| 推荐程度                     | 更推荐               | 可作为兼容补充 |

如果两者都存在，服务端通常优先使用 `If-None-Match` / `ETag`。

### 1.6 强缓存失效后会不会走协商缓存

会，但前提是本地缓存里有可用验证器。

示例一：强缓存过期后走协商缓存。

第一次响应：

```http
Cache-Control: max-age=60
ETag: "app.abc123"
```

60 秒内：

```text
浏览器直接使用本地缓存，不发请求
```

60 秒后：

```http
If-None-Match: "app.abc123"
```

服务器未变化：

```http
304 Not Modified
```

服务器已变化：

```http
200 OK
ETag: "app.def456"
```

示例二：强缓存过期后不能协商，只能重新请求。

第一次响应：

```http
Cache-Control: max-age=60
```

没有 `ETag`，也没有 `Last-Modified`。

60 秒后，浏览器没有条件请求字段可带，通常只能发普通请求，服务器返回：

```http
200 OK
```

### 1.7 304 到底表示什么

#### 1.7.1 304 表示文件发生变化了吗

不是。

`304 Not Modified` 的语义是：

> 服务端根据条件请求判断：客户端本地缓存的资源仍然可用，资源没有变化，浏览器继续使用本地缓存体。

所以发生协商缓存且返回 `304` 时：

- 浏览器确实向服务器发了请求。
- 服务器没有返回文件内容。
- 浏览器使用本地已有文件内容。
- 从 HTTP 语义上看，资源被判断为“未变化”。

#### 1.7.2 文件发生变化时返回 304 还是 200

文件发生变化时，正确行为应该是返回：

```http
200 OK
```

并返回新文件内容、新的 `ETag` 或新的 `Last-Modified`。

只有资源未变化时才应该返回：

```http
304 Not Modified
```

如果文件实际变化了但仍返回 `304`，通常说明服务端缓存判断有问题，例如：

- `ETag` 生成策略错误。
- `Last-Modified` 没有更新。
- CDN 或反向代理缓存配置错误。
- 构建产物覆盖方式导致修改时间未变化。
- Nginx / 对象存储返回了错误的验证头。

### 1.8 常见缓存配置组合

#### 1.8.1 SPA 的 index.html

推荐：

```http
Cache-Control: no-cache
```

含义：

- 浏览器可以保存 `index.html`。
- 每次打开页面前必须向服务端验证。
- 如果 `index.html` 未变化，可返回 `304`。
- 如果发布了新版本，应返回 `200` 和新的 HTML。

不建议给 `index.html` 配长强缓存。否则用户可能长期拿到旧 HTML，继续引用旧的 JS / CSS。

#### 1.8.2 带 hash 的 JS / CSS / 图片

推荐：

```http
Cache-Control: public, max-age=31536000, immutable
```

适用文件：

```text
app.8f3a1c2.js
chunk-vendors.a91bc3.css
logo.12ab.png
```

原因：

- 文件名 hash 变了就等于 URL 变了。
- 旧 URL 可以放心长期缓存。
- 新版本通过新的 URL 获取。

#### 1.8.3 不带 hash 的静态文件

推荐偏保守：

```http
Cache-Control: no-cache
```

或者短缓存：

```http
Cache-Control: public, max-age=300
```

不带 hash 的文件 URL 不变，强缓存太长容易导致用户拿旧资源。

#### 1.8.4 接口响应

普通业务接口通常推荐：

```http
Cache-Control: no-store
```

或者：

```http
Cache-Control: no-cache
```

选择依据：

- 数据敏感、登录态相关、实时性强：用 `no-store`。
- 可缓存但需要每次确认新鲜度：用 `no-cache`。
- 明确可短时间复用的公共接口：可用 `max-age=秒数`。

#### 1.8.5 登录、权限、用户信息

推荐：

```http
Cache-Control: no-store
```

避免浏览器或中间缓存保存敏感响应。

### 1.9 Vary 与缓存键

`Vary` 表示除了 URL 之外，还要把哪些请求头纳入缓存区分。

示例：

```http
Vary: Accept-Encoding
```

表示 gzip、br 等不同压缩版本要分开缓存。

常见值：

| Vary              | 含义                       |
| :---------------- | :------------------------- |
| `Accept-Encoding` | 按压缩方式区分缓存         |
| `Accept-Language` | 按语言区分缓存             |
| `Origin`          | 跨域场景按来源区分缓存     |
| `Authorization`   | 按认证信息区分缓存，需谨慎 |

注意：`Vary` 过多会降低缓存命中率。

### 1.10 DevTools 中怎么看缓存

#### 1.10.1 Network 面板常见表现

| 表现                | 含义                         |
| :------------------ | :--------------------------- |
| `200 OK`            | 网络请求成功，拿到响应体     |
| `304 Not Modified`  | 协商缓存命中，使用本地缓存体 |
| `from memory cache` | 内存缓存命中                 |
| `from disk cache`   | 磁盘缓存命中                 |
| Size 很小且状态 304 | 只传响应头，不传文件体       |

#### 1.10.2 Disable cache

DevTools 的 `Disable cache` 只在 DevTools 打开时生效。

它会让浏览器尽量绕过正常缓存策略，适合排查发布问题，但不能代表真实用户访问行为。

#### 1.10.3 普通刷新与强制刷新

| 操作                   | 常见行为               |
| :--------------------- | :--------------------- |
| 地址栏回车             | 更倾向复用强缓存       |
| 普通刷新               | 可能触发协商验证       |
| 强制刷新               | 尽量绕过缓存重新请求   |
| 清空缓存并硬性重新加载 | 清理本地缓存后重新拉取 |

不同浏览器版本和资源类型会有细节差异，排查时以 Network 面板实际请求头、响应头为准。

### 1.11 项目前端发布建议

#### 1.11.1 推荐 Nginx 静态资源策略

SPA HTML：

```nginx
location = /index.html {
    add_header Cache-Control "no-cache";
}
```

带 hash 的静态资源：

```nginx
location ~* \.(?:js|css|png|jpg|jpeg|gif|svg|webp|ico|woff2?)$ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}
```

SPA 兜底：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

#### 1.11.2 发布后页面空白的常见缓存原因

| 现象             | 可能原因                      | 排查方式                             |
| :--------------- | :---------------------------- | :----------------------------------- |
| 页面引用旧 JS    | `index.html` 被强缓存         | 检查 `index.html` 的 `Cache-Control` |
| JS 请求返回 HTML | 旧 HTML 引用了已删除的 chunk  | 看 JS 请求的 Response 是否是 HTML    |
| 用户刷新后恢复   | 协商缓存或强制刷新拿到新 HTML | 对比刷新前后的 `index.html` 响应头   |
| 部分用户异常     | CDN 节点缓存未刷新            | 检查 CDN 缓存和回源头                |

#### 1.11.3 Nginx 中开启或透传 ETag / Last-Modified

如果是 Nginx 直接托管静态文件，`Last-Modified` 通常由文件修改时间自动生成，`ETag` 默认也通常是开启状态；可以显式配置：

```nginx
location /tiles/ {
    alias /data/tiles/;

    etag on;
    if_modified_since exact;

    expires 30d;
    add_header Cache-Control "public, max-age=2592000";
}
```

字段含义：

| 配置                           | 作用                                                     |
| :----------------------------- | :------------------------------------------------------- |
| `etag on;`                     | 允许 Nginx 为静态文件响应生成 `ETag`                     |
| `if_modified_since exact;`     | 控制 Nginx 如何按 `If-Modified-Since` 判断是否返回 `304` |
| `expires 30d;`                 | 生成 `Expires`，并通常配合生成相应 `Cache-Control`       |
| `add_header Cache-Control ...` | 明确告诉浏览器强缓存时间和缓存属性                       |

如果是 Nginx 反代对象存储、瓦片服务商或后端服务，Nginx 一般不应凭空伪造 `ETag` / `Last-Modified`，更稳妥的是透传上游已有响应头：

```nginx
location /sispg-minio-upload/ {
    proxy_pass http://真实上游地址;

    proxy_pass_header ETag;
    proxy_pass_header Last-Modified;

    expires 30d;
    add_header Cache-Control "public, max-age=2592000";
}
```

如果上游本来返回了缓存头，但经过甲方 Nginx 后丢失，需要检查是否存在隐藏响应头的配置：

```nginx
proxy_hide_header ETag;
proxy_hide_header Last-Modified;
proxy_hide_header Cache-Control;
proxy_hide_header Expires;
```

不要为了“开启 Last-Modified”随便写：

```nginx
add_header Last-Modified $date_gmt;
```

因为 `$date_gmt` 每次响应都会变化，浏览器会认为资源修改时间一直在变，反而破坏协商缓存。

对地图瓦片、三维地形瓦片这类 URL 稳定、内容变更频率低的资源，通常优先补明确强缓存：

```nginx
location /sispg-minio-upload/ {
    proxy_pass http://真实上游地址;

    expires 30d;
    add_header Cache-Control "public, max-age=2592000";
}
```

如果瓦片 URL 带版本号或内容确定不可变，可以再加 `immutable`；如果 URL 不变但内容可能更新，应缩短 `max-age`，例如 `86400` 秒。

### 1.12 速记表

| 目标                   | 推荐配置                                             | 说明                       |
| :--------------------- | :--------------------------------------------------- | :------------------------- |
| HTML 及时更新          | `Cache-Control: no-cache`                            | 允许缓存，但每次验证       |
| hash 静态资源长期缓存  | `Cache-Control: public, max-age=31536000, immutable` | URL 变更即更新             |
| 敏感接口不落盘         | `Cache-Control: no-store`                            | 不保存缓存副本             |
| 每次都验证但可省响应体 | `Cache-Control: no-cache` + `ETag`                   | 未变化返回 304             |
| 先强缓存，过期后协商   | `Cache-Control: max-age=秒数` + `ETag`               | 新鲜期内不请求，过期后验证 |
| 兼容修改时间验证       | `Last-Modified`                                      | 精度弱于 ETag              |
