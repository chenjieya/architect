> “Vite 很快”几乎成了共识，但**快在哪里、为什么快、哪些地方刻意不做**，却很少有人说清楚。  
> 真正理解这一篇，你才能判断：**什么时候 Vite 会快，什么时候它并不占优势。**

---

## 1. 先给结论：Vite 的快不是“优化”，而是“避免工作”

一句话总结：

> **Webpack 在努力“把事情做快”，Vite 在努力“少做事情”。**

这一点贯穿全文。

---

## 2. 冷启动为什么几乎与项目规模无关？

### 2.1 Webpack 冷启动慢的根本原因

Webpack 启动时必须完成：

```text
解析入口
→ 构建完整依赖图
→ 执行 loader
→ 执行 plugin
→ 生成 bundle
→ 启动 dev server
```

**复杂度 ≈ O(项目总模块数)**

> 项目越大，启动越慢 —— 这是结构性问题。

---

### 2.2 Vite 冷启动做了什么？

Vite 启动时几乎只做三件事：

1. 启动一个 HTTP Server
2. 初始化插件系统
3. **不解析任何业务模块**

```ts
// Vite 启动阶段（抽象）
createServer().use(pluginContainer).listen()
```

📌 **没有依赖图，没有 bundle**

---

### 2.3 模块编译被“延迟”到什么时候？

> **第一次被浏览器请求时**

```text
启动 Server（毫秒级）
  ↓
浏览器请求 main.ts
  ↓
Vite 才开始处理 main.ts
```

所以：

- 100 个模块的项目 → 启动很快
- 10 万个模块的项目 → 启动依然很快

---

## 3. HTTP 并发：被忽略但极其关键的性能来源

### 3.1 Vite 把“并发能力”交给了浏览器

在 Vite 中：

```ts
import A from './A'
import B from './B'
import C from './C'
```

浏览器会：

```text
并发请求 A / B / C
```

而不是串行处理。

📌 **现代浏览器并发请求能力极强（6~10+）**

---

### 3.2 对比：Webpack 的“单点瓶颈”

Webpack Dev Server：

```text
浏览器
  ↓
请求 bundle.js
  ↓
Webpack 内部串行构建
```

👉 并发优势直接被抹掉。

---

## 4. 为什么 Vite 的 HMR 能“快到无感”？

### 4.1 Webpack HMR 的本质

Webpack HMR 是：

> **在一个巨大的 bundle 里，定位并替换模块**

这意味着：

- bundle 越大
- 替换成本越高
- 边界越模糊

---

### 4.2 Vite HMR 的结构性优势

Vite 的 HMR 前提是：

- 每个文件是独立模块
- 模块间通过 ESM import 连接

```text
Hello.vue 改动
  ↓
只重新请求 Hello.vue
```

📌 **不需要“重新算整个世界”**

---

### 4.3 HMR 的精确度来源

```ts
// Hello.vue
if (import.meta.hot) {
  import.meta.hot.accept()
}
```

- 只通知依赖这个模块的父模块
- 不影响无关模块

---

## 5. esbuild：快，但不是“全能”

### 5.1 esbuild 为什么快？

- Go 语言（编译型）
- 原生并发
- 极少 AST 转换

```ts
esbuild.transform(code, {
  loader: 'ts',
  target: 'esnext',
})
```

> esbuild 的目标是：**最快把代码变成能跑的 JS**

---

### 5.2 为什么不用 esbuild 打包？

因为它**不擅长**：

- 深度 Tree Shaking
- 复杂 chunk 切分
- 插件生态不成熟（相比 Rollup）

📌 **Vite 很清楚工具的边界**

---

## 6. 依赖预构建：快背后的“唯一一次慢”

### 6.1 为什么第一次启动可能慢？

第一次启动你可能看到：

```text
Optimizing dependencies...
```

这是因为 Vite 在做：

- 扫描 `node_modules`
- 用 esbuild 预构建依赖

---

### 6.2 这一步为什么是必要的？

如果不预构建：

- 一个库 → 上百个文件
- 浏览器 → 上百次请求
- HMR / 刷新都变慢

---

### 6.3 但它只做一次

```text
node_modules/.vite/
```

后续启动：

- 直接命中缓存
- 几乎零成本

---

## 7. 缓存策略：Vite 的“隐形加速器”

### 7.1 文件级缓存

```ts
// 若文件未改动
直接返回缓存结果
```

---

### 7.2 HTTP 缓存 + 304

```http
If-None-Match: xxx
```

📌 浏览器缓存也被充分利用。

---

## 8. 为什么说：Vite 的快是“反工程直觉”的？

传统工程思维：

> **提前做好所有事，运行时就会快**

Vite 的思维：

> **只在“被需要时”才做事**

这意味着：

- 开发体验极佳
- 但需要浏览器支持
- 也需要你理解其边界

---

## 9. Vite 不快的场景（非常重要）

你必须知道它的边界：

### ❌ 不适合的情况

- 老旧浏览器（无 ESM）
- 极端网络受限环境
- SSR 初学者乱用

### ⚠️ 需要注意

- 巨量动态 import
- 极复杂 monorepo（需调优）

---

## 10. 这一篇你真正应该记住的结论

1. **Vite 的快来自“架构延迟”**
2. **开发阶段不打包，是最大性能红利**
3. **HMR 的快，是模块边界清晰的自然结果**
4. **Vite 没有银弹，它只是选择更合理**
