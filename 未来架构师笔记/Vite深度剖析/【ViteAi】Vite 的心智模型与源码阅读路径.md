> 真正的专家，不是记住 API，  
> 而是**知道为什么它只能这样设计，而不能那样设计**。

---

## 1. 先给终极结论：Vite 不是一个工具，而是一套约束系统

一句话定性：

> **Vite 的本质，是对“现代前端工程边界”的一次系统性约束。**

理解这一点，你就不会再纠结“它为什么不支持 X”。

---

## 2. Vite 的三层心智模型（非常重要）

### 2.1 第一层：浏览器优先（Browser-first）

核心假设：

```text
浏览器是强的
ESM 是基础设施
```

后果：

- Dev 阶段不打包
- 每个文件即模块
- import 是运行时行为

👉 **这不是选择，是前提**

---

### 2.2 第二层：分阶段最优（Stage-oriented）

```text
Dev   → 快 + 精准
Build → 小 + 稳定
SSR   → 同构 + 可调试
```

后果：

- esbuild ≠ Rollup
- 插件多态执行
- 两套执行语义并存

---

### 2.3 第三层：最小职责原则（Minimal Responsibility）

Vite 明确不做：

- 框架层抽象
- 数据流管理
- 路由解决方案

👉 **只解决“模块如何运行”**

---

## 3. 如果你只能记住 5 个 Vite 设计原则

1. **延迟一切可延迟的工作**
2. **模块边界即系统边界**
3. **开发与生产目标永不妥协**
4. **工具为生态服务，不为兼容服务**
5. **可解释性 > 魔法**

---

## 4. Vite 源码的真实结构（宏观视角）

```text
packages/vite/
├── src/node/
│   ├── server/
│   ├── plugins/
│   ├── optimizer/
│   ├── ssr/
│   └── build/
```

📌 **不要“顺着文件读”，要“顺着问题读”**

## 6. 如何“正确地”读 Vite 源码？

### ❌ 错误方式

- 从入口一路往下
- 逐行理解
- 试图全读

---

### ✅ 正确方式

1. 先明确问题
2. 找对应模块
3. 顺着调用链走
4. 忽略细节，抓住边界

📌 **你不是在背源码，而是在验证设计**

---

## 7. 从“会用”到“会扩展”的跃迁路径

你可以用这个路径自检：

| 阶段 | 能力            |
| ---- | --------------- |
| 初级 | 写配置          |
| 中级 | 调 optimizeDeps |
| 进阶 | 写插件          |
| 高级 | Debug HMR       |
| 专家 | 改源码不慌      |

---

## 8. 如果你要参与 Vite 生态，你可以做什么？

- 写 **小而专一** 的插件
- 给文档提 PR
- 维护企业内 Vite preset
- 给框架写 Vite adapter

👉 **不要一开始就造“大而全”**

---

## 9. Vite 的“不可逆趋势”

你必须接受的事实：

- ESM 不会倒退
- 浏览器只会更强
- Dev 与 Build 的分离会成为常态

Vite 不是终点，但它定义了方向。
