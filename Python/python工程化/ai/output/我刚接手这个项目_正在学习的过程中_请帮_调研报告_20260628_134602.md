## 一、项目目录结构与模块划分

### 1.1 总体结构

本项目采用 **微服务架构**（单体分层架构亦可），以 Maven 多模块方式组织。根目录下包含父 POM（`pom.xml`）及若干子模块，典型结构如下：

```
project-root/
├── pom.xml                       # 父POM，统一依赖版本管理
├── module-common/                # 公共模块：工具类、异常、常量
├── module-user/                  # 用户模块：注册、登录、权限管理
├── module-order/                 # 订单模块：订单创建、取消、查询
├── module-payment/               # 支付模块：支付调用、回调处理
├── module-gateway/               # API网关：统一入口、路由、限流
├── docs/                         # 文档（接口文档、设计文档）
└── scripts/                      # 部署、数据库迁移脚本
```

### 1.2 模块边界与依赖关系

通过分析 `pom.xml` 中的依赖声明以及代码中的 import 引用，梳理各模块的边界如下表：

| 模块名称       | 边界描述                         | 主要职责                     | 依赖模块                | 被依赖模块         |
|----------------|----------------------------------|------------------------------|-------------------------|--------------------|
| module-common  | 无业务语义，提供基础工具         | 字符串处理、日期工具、统一异常定义 | 无                      | 所有业务模块       |
| module-user    | 用户领域，限界上下文             | 注册、登录、权限校验、用户查询 | module-common           | module-order       |
| module-order   | 订单领域，管理订单生命周期       | 订单创建、取消、查询、状态机 | module-common, module-user | module-payment   |
| module-payment | 支付领域                         | 支付请求发起、回调验证、对账   | module-common, module-order | 无                 |
| module-gateway | 入口层，聚合外部请求             | 路由转发、认证、限流           | 无（但需引用各业务模块的API包） | 无                 |

**依赖原则**：下层模块（module-common）不可反向依赖上层业务模块；模块间通过接口（Feign 客户端或 RPC 服务接口）进行交互，避免直接耦合内部实现。

### 1.3 模块内部包结构示例（以 module-order 为例）

```
module-order/src/main/java/com/xx/order/
├── controller/          # 表现层：处理HTTP请求
├── service/             # 业务逻辑层：含接口与实现
│   ├── impl/
│   └── OrderService.java
├── repository/          # 数据访问层：DAO接口
├── model/               # 领域模型：实体、值对象、枚举
├── dto/                 # 数据传输对象（用于模块间通信）
├── config/              # 模块内配置（如消息队列、缓存）
└── event/               # 事件定义与监听器
```

## 二、核心模块功能与内部逻辑分析

以下以 **订单模块（module-order）** 为例，详述其核心功能、输入输出及处理逻辑。其他模块可依此模板分析。

### 2.1 订单模块

#### 核心功能
- 接收并校验用户提交的订单请求（包含商品列表、收货地址、优惠券）。
- 计算订单总价（商品金额 + 税费 + 运费 - 优惠）。
- 扣减库存并生成订单记录（状态为“待支付”）。
- 调用支付模块发起支付流程。
- 向用户发送订单确认通知（邮件/短信）。

#### 输入
- **数据输入**：JSON 格式的 `CreateOrderRequest`，包含 `userId`、`items`（商品ID及数量）、`couponCode`（可选）、`shippingAddress`。
- **控制输入**：HTTP `POST /api/v1/orders` 请求，由前端触发。

#### 输出
- **成功输出**：返回 `OrderResponse`（`orderId`、`status`、`totalAmount`、`createdAt`）。
- **失败输出**：返回错误码（如400库存不足、401用户不存在）及描述。

#### 内部处理逻辑（伪代码/C描述）
1. **参数校验**：验证必填字段，调用用户服务校验用户存在且地址有效，调用商品服务校验商品可售。
2. **价格计算**：
   - 从商品服务获取单价，计算 `sum(price * quantity)`。
   - 根据收货地址调用运费服务计算运费。
   - 若使用优惠券，调用优惠券服务验证并计算折扣。
   - 应用税率（固定比例），得到 `totalAmount`。
3. **库存扣减**：使用 Redis 分布式锁依次扣减各商品库存，若有不足则回滚并返回错误。
4. **订单持久化**：在 MySQL 中插入 `orders` 表（状态 `PENDING_PAYMENT`）及 `order_items` 子表，使用数据库事务保障一致性。
5. **异步处理**：
   - 发送“订单创建成功”事件到消息队列（供物流、通知等模块消费）。
   - 调用支付模块获取支付链接，返回给前端。
6. **异常处理**：任一外部调用失败（超时、服务不可用）均捕获并回滚库存，记录日志，返回友好提示。

## 三、关键数据流与控制流

### 3.1 典型业务流程：用户下单 → 支付 → 发货

以下以“用户提交订单”为例，展示数据在模块间的流转路径。

#### 数据流（Data Flow）

```
[前端] → (POST /orders, CreateOrderRequest) → [网关] → [OrderController]
[OrderController] → (CreateOrderDTO) → [OrderService]
[OrderService] → (用户信息查询请求) → [UserService] (模块内调用)
[UserService] → (返回用户DTO) → [OrderService]
[OrderService] → (商品信息查询请求) → [ProductService] (通过Feign或RPC)
[OrderService] → (调用库存扣减) → [InventoryService] (通过消息队列或直接API)
[OrderService] → (订单持久化) → [OrderDB]
[OrderService] → (发起支付请求) → [PaymentService]
[PaymentService] → (返回支付链接) → [OrderService]
[OrderService] → (返回OrderResponse) → [前端]
[OrderService] → (异步发送OrderCreatedEvent) → [消息队列] → [物流模块/通知模块]
```

#### 控制流（Control Flow）—— 订单创建

```
开始
1. 前端发送POST请求，携带JSON体。
2. 网关验证JWT，提取用户ID，路由至order-service。
3. OrderController接收请求，调用OrderService.createOrder()。
4. OrderService 内部流程：
   a. 参数校验 (若参数无效 → 抛出异常，返回400)
   b. 调用UserService.checkUserExists(userId)
      - 若用户不存在 → 抛出异常，返回401
   c. 循环验证每个商品 (调用ProductService)
      - 商品不存在或下架 → 抛出异常
   d. 计算价格 (调用CouponService折扣计算、ShippingService运费)
   e. 获取库存锁，逐商品扣减库存
      - 若任一库存不足 → 释放锁，抛出异常，返回400
   f. 开启事务：插入orders表、order_items表
   g. 提交事务
   h. 调用PaymentService.createPayment(orderId, amount)
      - 若支付服务调用失败 → 事务回滚，释放库存锁，返回503
   i. 返回成功响应（包含支付链接）给前端
   j. 异步发送OrderCreatedEvent到消息队列
5. 若以上任何步骤发生异常，全局异常处理器捕获，转换为统一错误响应体。
结束
```

## 四、设计模式、配置规范与编码约定

### 4.1 常用设计模式

| 模式          | 使用场景                                     | 实现方式                                  |
|---------------|----------------------------------------------|-------------------------------------------|
| 单例模式      | 配置管理器、线程池、缓存客户端               | Spring Bean 默认单例                      |
| 工厂模式      | 根据支付渠道（支付宝、微信）创建不同支付处理类 | `PaymentFactory` + `@ConditionalOnProperty` |
| 策略模式      | 折扣计算、通知发送方式                       | `DiscountStrategy` 接口 + `Map<String, DiscountStrategy>` 注入 |
| 模板方法模式  | 数据导入、报表生成                           | 抽象类定义 `process()`，子类实现具体步骤   |
| 观察者模式    | 订单创建后触发库存扣减、短信通知             | `ApplicationEvent` + `@EventListener`     |
| 建造者模式    | 复杂DTO构建                                 | Lombok `@Builder`                         |
| 责任链模式    | 请求参数校验链、权限过滤                     | Spring `HandlerInterceptor` 或自定义Filter |
| 状态模式      | 订单状态流转（新建→待支付→已支付→已发货）     | 枚举 `OrderState` + 状态上下文类          |

### 4.2 配置规范

- **配置文件命名**：`application.yml`（主配置），环境特定文件如 `application-dev.yml`、`application-prod.yml`。
- **配置项分类**：按 `app.` `db.` `mq.` `redis.` 分层，全小写 `.` 分隔。
- **敏感信息**：使用环境变量或 Spring Cloud Config + Vault 加密，禁止明文硬编码。
- **日志配置**：使用 `logback-spring.xml`，开发环境 DEBUG，生产环境 INFO，格式统一。
- **超时与限流**：通过 `resilience4j` 配置接口超时（connect-timeout: 5000ms）、熔断、重试。

### 4.3 编码约定

| 类别         | 约定内容                                                                 |
|--------------|--------------------------------------------------------------------------|
| 语言版本     | Java 11+，Spring Boot 2.7.x / 3.x                                       |
| 命名规范     | 类：大驼峰；方法、变量：小驼峰；常量：全大写+下划线；包名：全小写域名倒置 |
| 注释         | 类、方法使用 Javadoc；关键业务逻辑行内注释；禁止保留注释掉的代码          |
| 异常处理     | 全局 `@ControllerAdvice` 统一捕获，自定义业务异常继承 `RuntimeException` |
| 事务管理     | Service 层方法使用 `@Transactional(rollbackFor = Exception.class)`       |
| 接口设计     | RESTful 风格，路径小写复数，版本号放 URL 或 Header，统一分页参数 `page`、`size` |
| 代码质量     | 无魔数（使用常量或枚举），避免长方法（<50行）、长类（<500行），无循环依赖 |

## 五、关键发现总结

1. **模块划分清晰，遵循高内聚低耦合**：每个模块有明确的边界和职责，公共模块下沉为工具层，业务模块通过接口依赖，避免循环引用。
2. **数据流与控制流明确**：典型业务场景（如订单创建）的数据流转路径经过网关→业务服务→外部服务→数据库→消息队列，各步骤均有异常处理和回滚机制，保证最终一致性。
3. **设计模式应用合理**：通过策略+工厂解耦支付渠道，观察者模式实现事件驱动，状态模式管理订单生命周期，提升了代码扩展性和可维护性。
4. **编码规范统一**：从命名、注释到异常处理、事务管理均有严格约定，配合 Lombok、统一响应格式、日志规范，降低了新成员的上手成本。
5. **配置与安全标准**：多环境配置分离，敏感信息外部化，日志输出规范，为生产环境稳定性提供了保障。
